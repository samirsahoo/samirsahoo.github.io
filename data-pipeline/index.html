Order Data Pipeline

How order CSV files travel from a landing directory into PostgreSQL: detection, registration, event hand-off, orchestrated batch import, validation, reject handling and daily reporting — and what keeps each hop safe under crashes, redeliveries and retries.

Runtime
Java 21 · Spring Boot 3.5
Processing
Spring Batch 5 · Cloud Task 3
Messaging
Cloud Stream 4.3 · RabbitMQ
Orchestration
Spring Cloud Data Flow 2.11
Storage
PostgreSQL · Liquibase

1. Overview

Upstream systems drop order files (*.csv) into a shared inbox directory. The pipeline turns each complete file into exactly one Spring Batch JobInstance, which validates every line, upserts good orders into the orders table and records bad lines in order_rejects. Nightly reporting jobs aggregate both into daily summary tables.

The design is deliberately split into small, independently scalable pieces connected by durable state:

Detect & register

file-poller — a long-running service that notices stable files, de-duplicates them and stages them atomically.

Hand off

A transactional outbox relays an IngestionRequested.v1 event to RabbitMQ with publisher confirms.

Launch

ingestion-event-consumer de-duplicates deliveries via an inbox table and launches the import task through the SCDF REST API.

Process

orders-batch — a short-lived Spring Cloud Task running ordersImportJob (one file per execution) or the summary jobs.

The ingestion_file table is the single source of truth for where every file is in its lifecycle; each component owns a well-defined slice of its state machine.

4. End-to-end flow

  1. File landsA producer writes orders-2026-10-20.csv into the inbox (in-progress names like .tmp/.part are ignored).
  2. Stability checkEvery 15 s the poller records size and mtime in file_observation. A file qualifies once it is ≥ 30 s old, unchanged across the required number of polls, and (optionally) has a ready marker.
  3. RegisterSHA-256 is computed; an ingestion_file row is inserted as RECEIVED and the identity key is claimed in file_identity. Losing the claim → DUPLICATE.
  4. StageThe file is atomically renamed to staging/<fileId>.csv (duplicates go to duplicates/).
  5. QueueIn one transaction the row becomes QUEUED and an IngestionRequested.v1 event is inserted into outbox_event.
  6. RelayEvery 2 s the outbox relay locks a batch (FOR UPDATE SKIP LOCKED), publishes to RabbitMQ and marks rows published only after a positive publisher confirm.
  7. ConsumeThe consumer validates the event, confines its location to allowed roots, claims the eventId in inbox_message and locks the file row.
  8. LaunchPOST /tasks/executions/launch on SCDF with name=orders-import and arguments=fileId=<uuid> correlationId=…. Row → LAUNCHED with the task execution id.
  9. ImportThe orders-batch task runs ordersImportJob: re-verify the file (path, size, checksum) → PROCESSING; read/validate/upsert in chunks of 500; skipped lines go to order_rejects.
  10. FinalizeThe file is moved to archive/yyyy/MM/dd/; counts are written and the row becomes COMPLETED. On failure it becomes FAILED and can be restarted from the last committed chunk.
  11. ReportNightly, the orders-reporting composed task recomputes the last 7 days of order_daily_summary and reject_daily_summary in parallel.

5. Stage 1 · file-poller

One poll cycle (FilePoller.poll(), cron */15 * * * * * UTC) does four things in order:

  1. Honour the runtime switch — if pipeline_switch['file-poller'].enabled is false, skip. Operators toggle it for all replicas through POST /actuator/poller.
  2. Take the cluster-wide lock — pg_try_advisory_lock on a dedicated connection. Only one replica scans at a time; if a pod dies, PostgreSQL drops the session and releases the lock, so there is no lease to expire.
  3. Recover unfinished registrations — rows left in RECEIVED by a crash are queued if the staged file exists, or marked REJECTED if the file vanished from the inbox.
  4. Scan — list up to max-files-per-poll (100) candidates oldest-first and register the complete ones.

Crash-safe registration (FileRegistrar)

StepActionIf the process dies right after…
TX1Insert ingestion_file (RECEIVED) and claim the identity in file_identity; mark DUPLICATE if the claim is lostNext scan finds the row by source_path and resumes staging
MoveAtomic rename into staging/<fileId>.csv (or duplicates/<fileId>-<name>)recoverUnfinished() sees the staged file and queues it
TX2RECEIVED → QUEUED and outbox insert in the same transactionNothing lost: the outbox relay publishes the event

The inbox and staging directories must be on the same filesystem so the claim is an atomic rename. The poller fails fast at startup if they are not, or if any directory is missing or not writable.

Duplicate detection — identity rules

identity-ruleKeyEffect
CHECKSUM (default)sha256:<hash>Same content is a duplicate regardless of file name — robust against re-sends under a new name.
NAME_AND_CHECKSUMname-sha256:<sha(name)>:<hash>A re-sent file with a new name is processed again.
NAME_AND_SIZEname-size:<sha(name)>:<size>Cheap heuristic, no content check.

The primary key of file_identity is the de-duplication point: exactly one file can win the insert … on conflict do nothing race.

Outbox relay (OutboxRelay)

  • Runs every relay-interval-ms (2 s); locks up to 50 due rows with FOR UPDATE SKIP LOCKED, so several replicas can relay in parallel without double-sending concurrently.
  • Sends via StreamBridge with headers x-correlation-id and eventType, then waits up to 10 s for the publisher confirm.
  • A row is marked published_at only on an ack that was not returned as unroutable. Failures set next_attempt_at with exponential back-off (2n s, capped at 5 min).
  • Gauge pipeline.outbox.pending exposes the backlog.

7. Stage 3 · ingestion-event-consumer

IngestionRequestHandler processes each delivery with at-least-once semantics:

  1. Validate — Bean Validation on the event and SafePaths.resolveWithin(allowedRoots, location), which rejects .. traversal, paths outside the roots and symlinks escaping a root. Invalid events are never retried.
  2. Claim the message in inbox_message (key: consumer name + eventId) with a 5-minute lease:
    • DONE already → acknowledge and ignore (duplicate delivery);
    • leased by another instance → throw, the binder retries later;
    • otherwise claimed, with an attempt counter.
  3. External events (no fileId) — register a new ingestion_file row directly as QUEUED with identity sha256:<hash>; duplicates are recorded and not launched.
  4. Lock the file row (SELECT … FOR UPDATE), verify that location and checksum match the registration, and skip if status is in LAUNCH_NOT_NEEDED (LAUNCHED, PROCESSING, COMPLETED, DUPLICATE, REJECTED).
  5. Launch the orders-import task via SCDF and, in the same transaction, set the row to LAUNCHED and the inbox entry to DONE.

Failure classification

SituationExceptionBehaviour
Bad payload, schema violation, unsafe path, mismatchInvalidEventExceptionNot retried → DLQ; inbox entry FAILED
SCDF 4xx (unknown definition, rejected request)PermanentLaunchExceptionNot retried → file LAUNCH_FAILED, message to DLQ
SCDF 5xx, timeout, connection error, 429TransientLaunchExceptionRetried: 4 attempts, back-off 2 s × 3 up to 60 s; after the last attempt → LAUNCH_FAILED + DLQ

Launch-then-crash is safe. If the consumer dies after SCDF accepted the launch but before its commit, the redelivered message launches again — and Spring Batch refuses the second execution because the JobInstance identified by fileId is already running or complete.

8. Stage 4 · orders-batch — ordersImportJob

A short-lived Spring Cloud Task. One file = one execution = one JobInstance. The job is prepareFile → importOrders → finalizeFile.

Step 1 — prepareFile (tasklet, re-runs on every restart)

  • Loads the ingestion_file row; refuses terminal statuses (COMPLETED, DUPLICATE, REJECTED).
  • Resolves the staged path inside PIPELINE_BATCH_ALLOWED_ROOTS and requires an existing, readable regular file.
  • Enforces max-file-size-bytes (512 MiB) and re-computes SHA-256 against the registered checksum.
  • Any of these failing marks the row REJECTED in a REQUIRES_NEW transaction (so it survives the step rollback) and fails the job.
  • Otherwise sets PROCESSING with the job and task execution ids and stores the input path in the job execution context.

Step 2 — importOrders (chunk-oriented, fault tolerant)

ComponentImplementation
ReaderFlatFileItemReader, UTF-8, header verified (BOM-tolerant, case-insensitive), RFC 4180 tokenizer with strict column count, saveState=true for restart
ProcessorOrderValidationProcessor — validates and normalises one line into an OrderRecord
WriterJdbcBatchItemWriter with an idempotent upsert on order_id that only updates when business columns actually changed
Chunk size500 items per transaction
Skip policyInvalidOrderException, FlatFileParseException; limit 1000 per file (exceeded → job fails)
Retry policyTransientDataAccessException, 3 attempts
Skip listenerRejectRecorder writes order_rejects inside the chunk transaction; unique (file_id, line_number) makes replays harmless

Step 3 — finalizeFile

  • Moves the input to archive/yyyy/MM/dd/ (if archive-dir is set). Idempotent: if the source is gone and the target exists, a previous attempt already archived it.
  • Computes written as the sum of the import step's write counts across all executions of the JobInstance, and rejected from order_rejects, so counts are correct after restarts.
  • Marks the row COMPLETED with records_read / written / rejected and the final path.

A job listener sets the MDC (fileId, jobExecutionId, correlationId) for the whole run and marks the row FAILED with the collected failure messages if the job does not complete. fail-on-job-failure=true makes the task exit non-zero so SCDF and Kubernetes see the failure.

Spring Batch / Cloud Task metadata lives in the dataflow schema with the BOOT3_ prefix when SCDF launches the task. Task pods set pipeline.db.search-path=dataflow,pipeline, so a single connection sees both schemas and chunk writes commit atomically with the batch metadata.

13. Schema management

  • Liquibase owns the schema, and only the db-migrator runs it. All services set spring.liquibase.enabled=false.
  • Release tags: every release ends with a tagDatabase changeSet. Each service declares pipeline.schema.required-tag (currently release-1.1.0); SchemaCompatibilityGuard fails startup if the tag is missing.
  • Expand / contract: between releases only additive changes ship (e.g. 1.1.0 adds nullable ingestion_file.correlation_id), so an N app works on schema N+1 during rolling upgrades. Destructive changes carry the label contract and are excluded by the default label filter !contract.
  • Framework tables: for standalone (non-SCDF) runs the migrator executes the official Spring Batch 5 / Cloud Task 3 PostgreSQL scripts from the framework jars. Disable with pipeline.migration.framework-schema.enabled=false when only SCDF is used.
  • Concurrency: DATABASECHANGELOGLOCK serialises concurrent migrators; the migrator verifies expected-tag as a post-condition and exits non-zero on failure, failing the deployment.

Correlation & logging

A correlationId is generated at registration and carried in the ingestion_file row, the event payload, the x-correlation-id message header and a non-identifying job parameter. Every log line includes it via MDC:

INFO [corr=c2d7…] [file=0b9e…] [job=17]  Import completed: written=3 rejected=1

Logs contain line numbers and reason codes only — never full record contents.
