Claude Across the SDLC

A phase-by-phase playbook for using Claude in software delivery — discovery, requirements, architecture, implementation, testing, code review, security, documentation, CI/CD and release, operations and incidents, maintenance and migrations, plus IT activities beyond code — with the right model, example prompts, verification and human checkpoints for each.

Simple definition#

Using Claude across the software development lifecycle (SDLC) means giving it a defined job in each phase — not just autocomplete while coding. In every phase the pattern is the same: context in (the artefacts that phase needs), a specific task, a verification step, and a human decision where accountability sits.

The lifecycle at a glance#

Phase Claude’s job Typical surface Model · effort Verification Human owns
Discovery & requirements Synthesise inputs, draft stories and acceptance criteria, find gaps Claude app, Projects Opus high Stakeholder review, traceability Scope and priority
Architecture & design Generate options, trade-offs, ADR drafts, threat models Claude app, Claude Code (plan mode) Opus/Fable high–xhigh Architecture review board The decision
Build Implement features, refactor, explain code Claude Code Opus xhigh; Sonnet for routine Compile, tests, lint, run The merge
Test Generate unit/integration/property tests, test data, find gaps Claude Code, CI Sonnet medium–high Mutation score, coverage of risky paths Test strategy
Review & security First-pass review, vulnerability analysis, dependency checks /code-review, /security-review, CI action Sonnet/Opus high Reproduce each finding Approval
CI/CD & release Write pipelines and IaC, explain failures, draft release notes Claude Code, headless in CI Sonnet medium Pipeline green, policy checks Go/no-go
Operate & incidents Summarise alerts and logs, propose hypotheses, draft post-mortems Agent with read-only MCP tools Sonnet; Haiku for triage Evidence from telemetry Incident command
Maintain & migrate Upgrades, framework migrations, dead-code removal, docs refresh Claude Code, batch + parallel worktrees Opus xhigh Full test suite, canary Rollout

Discovery and requirements#

Context in: interview notes, support tickets, process documents, existing API contracts, regulatory text.

  • Turn raw notes into user stories with acceptance criteria in Given/When/Then form.
  • Ask Claude to find ambiguities, contradictions and missing non-functional requirements (performance, availability, audit, data retention, accessibility).
  • Generate edge cases from the business rules — these become test cases later.
  • Use Claude Projects (or a shared knowledge base) so every conversation sees the same domain material.

TipExample prompt

“Here are the refund policy, three support tickets and the current Refund API spec. Draft user stories with Given/When/Then acceptance criteria for partial refunds. Then list every question a product owner must answer before development can start, and every non-functional requirement the documents imply but do not state.”

Watch out: Claude will fill gaps with plausible assumptions. Ask it to mark assumptions explicitly, and have the product owner resolve them.

Architecture and design#

Context in: requirements, current architecture (C4 diagrams, ADRs), constraints (cloud, compliance, team skills), quality attribute targets.

  • Generate options, not answers: ask for two or three designs with explicit trade-offs against your quality attributes.
  • Draft ADRs in your template; draw diagrams as Mermaid or C4 from the codebase.
  • Threat-model the design (STRIDE per component and data flow).
  • Challenge a design: “Act as the architecture review board. What fails first at 10× load? What is the blast radius of each dependency failing?” — then check the answers against the review framework.
  • In Claude Code, plan mode on the real repository grounds design in the code that exists.

Watch out: models are persuasive. Treat a confident trade-off analysis as a hypothesis; validate key numbers (latency, cost, limits) with spikes and documentation.

Build#

Context in: the repository, CLAUDE.md, the story and acceptance criteria, related tests.

  • Follow the explore → plan → implement → verify loop (Claude Code in practice).
  • Give one task per session with a clear definition of done: “Implement partial refunds per story PAY-412. Done when ./mvnw verify passes and the new endpoint is in openapi.yaml.”
  • Use test-first where possible: have Claude write failing tests from the acceptance criteria, review the tests, then implement.
  • For refactoring, ask for behaviour-preserving steps with tests run after each.
  • Use Claude to explain unfamiliar code before changing it — especially legacy modules with no documentation.

Test#

  • Unit and integration tests from acceptance criteria and from the code’s branches.
  • Property-based tests for business invariants (“refund total never exceeds captured amount”).
  • Test data that respects schemas and privacy rules (synthetic, never copied production PII).
  • Gap analysis: “Which behaviours in RefundService have no test? Which tests would still pass if the logic were wrong?” — then confirm with mutation testing.
  • End-to-end and UI checks with browser automation where it pays off.

Common mistakeTests that test the implementation

Generated tests often mirror the code they were written from, so they pass even when the logic is wrong. Write tests from the requirements, review them before implementing, and use mutation testing to check they can fail.

Code review and security#

  • Run automated first-pass review on every PR (Claude Code action or /code-review): correctness, error handling, concurrency, API compatibility, adherence to CLAUDE.md rules.
  • Run /security-review or a security sub-agent on changes that touch authentication, input handling, crypto, deserialisation or infrastructure.
  • Ask for findings with evidence — file, line, failing scenario — and tell it to report nothing rather than style nits.
  • Combine with deterministic tools (SAST, dependency and secret scanning, licence checks); Claude explains and prioritises their findings and proposes fixes.

Human owns: approval. AI review adds a reviewer; it does not replace the accountable one, especially for security-sensitive code.

CI/CD and release#

  • Author and refactor pipelines (GitHub Actions, GitLab CI, Jenkins) and infrastructure as code (Terraform, Helm, Kubernetes manifests).
  • Explain failing builds: feed the log and diff; get a root-cause hypothesis and a fix.
  • Generate release notes and changelogs from merged PRs; draft migration guides for breaking changes.
  • Run Claude headless in CI for repeatable jobs (review, triage, dependency upgrade PRs) with least-privilege tokens.

WarningPlan before apply

Never let an agent terraform apply, kubectl apply to production or rotate credentials unattended. Have it produce a plan or PR; a human (or a policy-checked pipeline) applies.

Operate and incidents#

  • Alert triage: summarise and group alerts, link them to recent deploys (Haiku is often enough).
  • Investigation: an agent with read-only MCP tools for logs, metrics, traces and deploy history proposes hypotheses ranked by evidence.
  • Runbooks: turn tribal knowledge into runbooks; keep them in Git and in a skill the agent can load.
  • Post-mortems: draft the timeline and contributing factors from the incident channel and telemetry; humans write the actions.

Human owns: the incident command and every change to production.

Maintain and migrate#

Maintenance is where coding agents save the most time, because the work is large, repetitive and verifiable:

  • Framework and language upgrades (Spring Boot 3 → 4, Java 17 → 21, Python 2 leftovers), applied module by module with the test suite as the gate.
  • Dependency upgrades with release-note reading and breaking-change fixes.
  • Large mechanical changes across many repositories: split the work, run sessions in parallel worktrees or as batch jobs, and land small PRs.
  • Legacy understanding: document COBOL, PL/SQL or undocumented services; extract business rules before rewriting them.
  • Documentation refresh: keep READMEs, API docs and diagrams in sync with the code.

Common mistakes#

Common mistakeUsing Claude only in the build phase

Most defects and cost originate in requirements and design. An hour of Claude-assisted gap analysis on requirements can save weeks of rework.

Common mistakeNo human checkpoint at the risky step

Automating review, release or production changes end-to-end removes accountability. Keep explicit human decisions at scope, design, merge, release and production change.

Common mistakeMeasuring activity instead of outcomes

More PRs and more lines are not the goal. Track lead time, change failure rate, escaped defects and time to restore.

Review questions#

Where in the SDLC does Claude add the most value, and why? Usually in requirements and design (finding gaps early, generating options) and in maintenance (large, repetitive, test-verifiable change). Build-phase gains are real but depend on good tests and review.

How would you introduce AI code review without slowing teams down? Run it automatically on every PR as an additional reviewer, report only evidence-backed defects, tune it with CLAUDE.md rules, and keep human approval unchanged; measure false-positive rate and review time.

What should an incident-response agent be allowed to do? Read logs, metrics, traces and deploy history through read-only tools, propose hypotheses and draft communications — never change production without a human decision.

Summary#

  • Give Claude a defined job per phase: context in, specific task, verification, human decision.
  • Biggest leverage: requirements gap analysis, design options, maintenance and migrations.
  • Keep humans at scope, design, merge, release and production change.
  • Pair Claude with deterministic tools (tests, SAST, policy checks) — it explains and fixes; tools verify.
