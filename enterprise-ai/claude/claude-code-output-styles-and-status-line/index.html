Claude Code Output Styles and Status Line

Shaping how Claude Code responds and what you see while it works: the built-in output styles (Proactive, Concise, Explanatory, Learning), writing custom styles and when to use another feature instead, and building a status line that shows model, context, cost, git and rate limits.

Simple definition#

An output style changes how Claude talks to you for a whole session — its role, tone, length and format — by adding instructions to every request. The status line changes what you see while it works: a bar under the prompt rendered by your own script from live session data (model, context use, cost, git branch, rate limits). Neither changes what Claude is allowed to do.

Version noteSource and date

Condensed from Anthropic’s Output styles and Customize your status line, read on 7 November 2026.

Built-in output styles#

Style What changes Use it when
Default No extra instructions — Claude Code’s standard software-engineering prompt Most work
Proactive Starts work at once, makes reasonable assumptions instead of asking about routine decisions; still checks before deleting data or touching shared/production systems You’d rather correct a wrong assumption than answer questions
Concise Leads with the result; no preamble, narration or recap; simple answers in 1–3 sentences (errors, test output and safety warnings stay full) Default answers are longer than you want
Explanatory Adds short ★ Insight blocks explaining the choices behind the code Learning a codebase; wanting the reasoning
Learning Insights plus TODO(human) spots where you write the interesting part, then Claude continues Hands-on practice while the task still gets done

Proactive does not change your permission mode; prompts still appear as before.

Switching#

Where How
Terminal /output-style concise, or /config → Output style
Settings "outputStyle": "Explanatory" — case-sensitive (explanatory silently means Default)
Default everywhere outputStyle in ~/.claude/settings.json (project files override it)
VS Code / → Output styles

The command and menu save to .claude/settings.local.json. A switch applies from your next message (the first message after a switch is an uncached turn).

Custom output styles#

---
name: Diagrams first
description: Lead every explanation with a diagram
keep-coding-instructions: true
---
When explaining code, architecture or data flow, start with a Mermaid diagram of the
structure, then explain in prose. Use flowchart TD for control flow and sequenceDiagram
for request paths. Keep diagrams under 15 nodes.
Location Scope
~/.claude/output-styles/*.md You, all projects
.claude/output-styles/*.md The project (nearest directory wins)
Managed settings directory .claude/output-styles/ Organisation
Plugin output-styles/ As plugin:name; force-for-plugin: true applies it automatically
Frontmatter Does
name, description Shown in the picker (name defaults to the file name)
keep-coding-instructions true keeps Claude Code’s built-in engineering instructions (scoping changes, comments, verifying work). Default false — leave it out only if Claude won’t be writing code
force-for-plugin Plugin styles only: apply whenever the plugin is enabled

Key conceptKeep the coding instructions

A custom style without keep-coding-instructions: true drops Claude Code’s own guidance on how to scope and verify changes. For a style that changes tone on a coding project, always set it.

Styles apply to the main conversation and to forks; ordinary sub-agents keep their own system prompts. Style files are read at start-up — restart after editing one.

Output style or something else?#

You want Use
Every response in a voice, length or format; Claude in a different role Output style
Claude to know project conventions and commands CLAUDE.md
Instructions for one kind of task A skill
Something that must always happen A hook
A focused helper with its own tools and model A sub-agent
An addition to the system prompt for one launch --append-system-prompt

Status line#

/statusline show model, git branch, context % as a bar, and session cost

/statusline writes a script in ~/.claude/ and wires it up. Or configure it yourself:

{
  "statusLine": { "type": "command", "command": "~/.claude/statusline.sh", "padding": 2 }
}

Your command receives session JSON on stdin and prints one or more lines (ANSI colours and OSC 8 links work). It runs at session start, then after each assistant message, /compact, mode or vim changes, and on an optional refreshInterval, debounced at 300 ms. Read COLUMNS for width — tput cols doesn’t work inside it.

Most useful fields#

Field Contains
model.display_name Current model
workspace.current_dir, workspace.project_dir Where you are; where you started
context_window.used_percentage Context used (pre-calculated)
context_window.context_window_size 200k or 1M
cost.total_cost_usd Estimated session cost (client-side, list price)
cost.total_duration_ms, cost.total_lines_added/removed Time and churn
effort.level, fast_mode, output_style.name Session settings
rate_limits.five_hour.used_percentage, .seven_day… Plan limit use
prompt_cache.warm, prompt_cache.expires_at Whether the cache is still warm
pr.number, pr.review_state Open PR for this branch
worktree.name, session_name, agent.name, vim.mode Session identity

Example script#

#!/bin/bash
input=$(cat)
MODEL=$(jq -r '.model.display_name' <<<"$input")
PCT=$(jq -r '.context_window.used_percentage // 0' <<<"$input" | cut -d. -f1)
COST=$(jq -r '.cost.total_cost_usd // 0' <<<"$input")
BRANCH=$(git -C "$(jq -r '.workspace.current_dir' <<<"$input")" branch --show-current 2>/dev/null)
FILLED=$((PCT / 10)); BAR=$(printf '%*s' "$FILLED" '' | tr ' ' '▓')$(printf '%*s' $((10-FILLED)) '' | tr ' ' '░')
printf '%s · %s · %s %s%% · $%.2f\n' "$MODEL" "${BRANCH:-no-git}" "$BAR" "$PCT" "$COST"

Cache slow operations (git status in a big repo, API calls) to a temp file keyed by session ID. subagentStatusLine lets a second script rewrite the sub-agent task rows.

Troubleshooting the status line#

Symptom Check
Nothing appears Script executable? Prints to stdout? disableAllHooks also disables it
-- or empty values Field absent until the first API response; use // 0 defaults
Links not clickable Terminal must support OSC 8 (iTerm2, Kitty, WezTerm)

Common mistakes#

Common mistakeUsing a style as a rule

A style is an instruction; nothing enforces it. “Never edit migrations” belongs in a hook or deny rule, not a style.

Common mistakeLowercase style names in settings

"outputStyle": "concise" doesn’t match Concise and silently gives you Default.

Common mistakeExpensive status lines

The script runs after every message. A slow git status or network call makes the UI lag — cache it.

Review questions#

What does keep-coding-instructions: true do? Keeps Claude Code’s built-in software-engineering instructions alongside your custom style; without it a custom style replaces them.

Does the Proactive style let Claude run commands without asking? No. It changes how readily Claude makes decisions; your permission mode still decides what runs without a prompt.

Where does the status line get its data? From session JSON that Claude Code passes to your command on stdin each time it refreshes.
