Using Claude Intelligently

The practices that separate effective from wasteful Claude use: context engineering, prompting current models, verification loops, delegation and sub-agents, cost control, enterprise security and governance, measuring productivity, and the anti-patterns to avoid — with a one-page checklist.

Simple definition#

Using Claude intelligently means getting reliable, verified results at the lowest sensible cost and risk. It rests on five habits: give the right context, ask for a clear outcome, make the result verifiable, pick the right model and effort, and keep a human accountable for what ships.

1. Context engineering beats prompt tricks#

Claude knows a lot about software in general and nothing about your system. Quality depends mostly on what you put in the context window (prompt and context engineering).

Give it Example
The goal and why “We need partial refunds because finance reconciles daily; amounts must match the ledger to the cent.”
Constraints Framework versions, architecture rules, performance and compliance limits
Definition of done Commands to run, behaviour to observe, files that must change
Pointers, not dumps “The refund flow starts in RefundController; rules are in domain/refund” — let it read the rest
Examples One good existing endpoint, test or ADR to imitate
What not to do Paths not to touch, patterns the team has rejected, with the reason

Key conceptExplain the why

Current models generalise from reasons far better than from rules. “Never log card numbers — logs are shipped to a third-party SaaS” produces better behaviour across cases than “NEVER LOG PAN” in capitals.

2. Prompting current models#

  • Be direct and specific. Say what you want, in what format, at what length. Ask for action (“change the code”) when you want action, and for analysis when you want options.
  • Drop old workarounds. Shouting (ALWAYS, MUST), “think step by step”, role-play scaffolding and long rule lists were for weaker models; on current models they can make output worse. Use effort to control depth.
  • Structure long inputs. Put large documents first and the question last; label sections (for example with XML-style tags) so instructions and data are not confused.
  • Ask for uncertainty. “If something is ambiguous, list the assumption you made” or “say you don’t know rather than guess”.
  • Iterate on the prompt like code. Keep prompts in version control and evaluate changes on a fixed set of cases.

3. Verification is the multiplier#

Claude’s output is a draft until something checks it. The more automatic the check, the more you can delegate.

  • Give Claude the means to check itself: test commands, a running app, browser automation, schemas.
  • Ask it to show evidence: test output, quoted source lines, citations.
  • For important answers, use an independent check — a second session reviewing the first, a different model as judge, or a deterministic tool.
  • Be most sceptical of numbers, versions, API names and citations — the classic hallucination surface. Verify against source.

4. Delegation and parallelism#

  • Right-size the task: one coherent outcome per session; split large work into reviewable pieces.
  • Use sub-agents for broad reading and narrow specialist checks, so the main context keeps conclusions only; give them cheaper models and read-only tools where possible.
  • Run independent tasks in parallel (worktrees, batch jobs) and merge through normal PR review.
  • Give long tasks a budget and checkpoints: progress notes, a task list, intermediate commits — so a failed run can resume, not restart.

5. Cost control#

Free wins first, trade-offs second:

Order Lever Typical saving
1 Prompt caching for stable prefixes (system prompt, tools, documents) Large on repeated context; also faster
2 Input hygiene: send pointers and relevant extracts, not whole repositories; clear old tool results Proportional to context trimmed
3 Batches for anything not interactive 50%
4 Effort per route: low for chat and classification, higher only where measured Often several × on output tokens
5 Model per route: Haiku/Sonnet where they clear the bar Up to 40× between tiers
6 Loop hygiene in agents: stop conditions, task budgets, no retry storms Prevents runaway bills

TipMeasure cost per completed task

A cheaper request that needs three retries and a human fix is not cheaper. Track cost per successfully completed task, per route, from the usage fields you log.

Set spend limits and alerts per workspace or team, and review the top routes by cost monthly.

6. Security, privacy and governance#

Concern Practice
Data use Know your agreement: commercial API and enterprise plans are not used for training by default; zero data retention (ZDR) is available for eligible features and organisations — some newer features and models require standard retention, so check before you design.
Residency and hosting Use inference_geo, or run through Bedrock, Vertex AI or Foundry to stay inside existing regions, networks and contracts.
Secrets Never paste secrets into prompts; deny agent access to .env and key stores; use workload identity instead of static keys.
Prompt injection Treat web pages, tickets, emails, files and tool output as untrusted; least-privilege tools; human approval for irreversible actions (AI security).
Code provenance AI-written code goes through the same review, scanning and licence checks as human code; record AI assistance in PR templates if your policy requires it.
Access control SSO, role-based access, workspace separation, admin-managed settings and MCP allowlists for Claude Code.
Audit and observability Central logging of API usage and Claude Code telemetry (OpenTelemetry); retention per policy.
Policy and regulation Map use cases to your AI policy and regulations such as the EU AI Act; keep a register of AI use cases and owners (AI governance).

7. Measuring productivity honestly#

  • Use delivery outcomes: lead time for changes, deployment frequency, change failure rate, time to restore, escaped defects, review turnaround.
  • Add developer experience signals: survey satisfaction, time spent on toil versus design.
  • Compare like with like — similar work, before and after, or teams with and without — and watch for quality regressions that show up weeks later.
  • Avoid vanity metrics: lines generated, suggestions accepted, prompts sent.

Anti-patterns#

Common mistakeOutsourcing understanding

Merging code nobody on the team understands creates a maintenance liability. Ask Claude to explain the change; if you cannot explain it in review, do not merge it.

Common mistakeTrusting confidence instead of evidence

Fluent, confident answers are not evidence. Require tests, sources or reproduction.

Common mistakeOne model, maximum effort, for everything

Wastes money on easy work and adds latency. Tune model and effort per route.

Common mistakeEndless correction in one session

After two failed corrections, the context is polluted with wrong attempts. Clear, restate the task with what you learned, and start again.

Common mistakeAgents with production power

Unattended agents with write access to production, payments or customer communications turn small mistakes into incidents. Keep irreversible actions behind human approval.

Common mistakeShadow AI

Engineers pasting proprietary code into unapproved consumer tools. Provide an approved, convenient option with clear policy instead of only banning.

Checklist#

  • Task has a goal, the reason, constraints and a definition of done.
  • Context gives pointers and examples, not whole-repository dumps.
  • Model and effort chosen per route and validated on an evaluation set.
  • Output is verified by tests, tools or sources — not by the model’s confidence.
  • Prompt caching on stable prefixes; batches for offline work; usage logged.
  • Secrets denied; untrusted inputs treated as data; irreversible actions need approval.
  • A named human reviews and owns what ships.
  • Success measured by delivery outcomes, not activity.

Review questions#

Why do outdated prompting techniques hurt current models? They were compensations for weaker models. Current models follow instructions closely, so shouted rules and rigid scaffolding cause over-literal or over-cautious behaviour; clear goals with reasons and the effort setting work better.

How do you decide how much to delegate to Claude? By how cheaply and reliably the output can be verified: fully delegate what tests or tools check, delegate with review what a human can check quickly, and use assistance only where verification needs expert judgement.

What are the first three levers to cut a Claude bill? Prompt caching on stable prefixes, trimming input to what the task needs, and moving non-interactive work to batches — before trading quality through lower effort or smaller models.

Summary#

  • Context, clear outcomes and verification matter more than clever prompts.
  • Delegate in proportion to how verifiable the result is.
  • Cut cost with caching, input hygiene and batches first, then effort and model per route.
  • Govern data, secrets, injection risk and accountability; measure outcomes, not activity.
