Claude Models and Model Selection

The Claude model family in November 2026 — Fable, Opus, Sonnet and Haiku — with context windows and prices, how adaptive thinking and effort levels work, a task-to-model guide for product and engineering work, routing and fallbacks, and how to run your own selection.

Simple definition#

Anthropic sells Claude in tiers. Bigger tiers reason better and cost more; smaller tiers are faster and cheaper. Inside each model you also choose an effort level — how hard the model thinks before it answers. Model selection for Claude is therefore a two-dimensional choice: which tier and how much effort, made per task and checked against your own evaluation set.

Why it matters#

Between the cheapest and the most capable current Claude model the price differs by 100× per token. Effort changes token use within one model by several times again. Teams that pick “the best model, maximum effort” for everything overspend; teams that pick the cheapest for everything ship wrong answers. The general method is in Model selection for the enterprise; this article applies it to Claude.

The model family (November 2026)#

Model API model ID Context Max output Input / output price per 1M tokens Positioning
Claude Fable 5.1 claude-fable-5-1 1M 128K $10 / $50 Most capable widely released model: hardest reasoning, long-horizon autonomous work
Claude Opus 5.5 claude-opus-5-5 1M 128K $4 / $20 The default for serious work: complex coding, agents, analysis
Claude Sonnet 5.5 claude-sonnet-5-5 1M 128K $2 / $10 Speed and capability for everyday coding, agents and enterprise workloads
Claude Haiku 5.5 claude-haiku-5-5 1M 128K $0.10 / $0.50 (≤100K-token prompts) High-volume, latency-sensitive tasks: classification, extraction, routing, sub-agents

Prices are Anthropic first-party API list prices; Microsoft Foundry bills at the same rates, while Amazon Bedrock and Google Vertex AI publish their own pricing. Previous generations (Claude Fable 5, Opus 5, Opus 4.8, Sonnet 5, Haiku 4.5 and others) remain available for a time but should not be chosen for new work. Claude Mythos 5.1 has Fable-level capability but is available only to Project Glasswing participants.

TipNever hard-code what you can look up

The Models API (GET /v1/models) returns each model’s context window, output limit and capabilities. Read limits from it in tooling, and keep model IDs in configuration — not scattered through code — so an upgrade is a one-line change plus an evaluation run.

Discounts that change the arithmetic#

Mechanism Effect Use it for
Prompt caching Cache reads are billed at a small fraction of the input price (for example $0.20 per 1M on Opus 5.5 and Sonnet 5.5) Long, stable system prompts, documents and tool definitions reused across requests
Message Batches 50% off, results within 24 hours Offline work: back-fills, evaluations, bulk classification, nightly reports
Fast mode (Opus 5.5, Claude API only) Up to 2.5× faster output at 2× the price ($8 / $40) Interactive coding sessions where waiting costs more than tokens

Thinking and effort#

Current Claude models think before they answer — they reason internally, then respond. You do not set a thinking-token budget any more; instead:

  • Adaptive thinking lets the model decide how much to think per request. On Fable 5.1 and Opus 5.5 thinking is always on; on Sonnet 5.5 and Haiku 5.5 it is on by default.
  • Effort (low, medium, high, xhigh, max) sets the overall thoroughness: how much it thinks, how many tool calls it makes, how much it writes. It is the main quality-versus-cost dial within one model.
Effort Typical use
low Chat, classification, simple extraction, sub-agents doing narrow reading tasks
medium Default on Opus 5.5 and Haiku 5.5; most product features; agentic coding on Sonnet 5.5
high Intelligence-sensitive work: design, analysis, tricky debugging; default on Sonnet 5.5
xhigh Long agentic coding and multi-step tool use; the default in Claude Code
max When correctness matters far more than cost and measurement shows headroom above xhigh

Key conceptTry a better model at lower effort before a cascade

The newest models at low or medium effort often match or beat older models at high effort. Before building a multi-model cascade, measure the single most capable model at a lower effort on the same tasks — one model is simpler, and prompt caches are per model, so a cascade forfeits cache reuse.

Which model for which task#

Task Starting point Why
Architecture options, threat models, migration strategy Opus 5.5 high/xhigh; Fable 5.1 for the hardest Reasoning quality dominates cost; volume is low
Agentic coding (feature work, refactors, bug fixes) Opus 5.5 xhigh in Claude Code; Sonnet 5.5 medium–high for routine changes Long tool loops reward capability; routine edits do not need the top tier
Code review on every pull request Sonnet 5.5 high; Opus 5.5 for security-critical repos Runs often; must be good but not maximal
Test generation, documentation, changelogs Sonnet 5.5 medium Well-specified, verifiable output
Log and ticket triage, classification, routing Haiku 5.5 low High volume, short outputs, latency matters
RAG answer generation for employees Sonnet 5.5 medium; Haiku 5.5 for simple FAQ Grounded answers rarely need frontier reasoning
Bulk extraction from documents Haiku 5.5 or Sonnet 5.5 via Batches 50% batch discount; quality checked by sampling
Sub-agents that read and summarise for a lead agent Haiku 5.5 or Sonnet 5.5 low Keeps the expensive model’s context and bill small
LLM-as-judge in evaluation pipelines Same tier as, or above, the model being judged A weaker judge cannot reliably grade a stronger model

Routing, fallbacks and lock-in#

  • Route per use case, not per request, until you have data. A fixed model and effort for each route (review, triage, chat, extraction) is easy to evaluate and explain. Add dynamic routing only when traffic is varied enough to justify a classifier.
  • Handle refusals. Claude’s safety classifiers can decline a request (HTTP 200, stop_reason: "refusal"). Always check stop_reason before reading content. On the Claude API you can enable server-side fallbacks so a declined request is retried automatically on a suitable model; on Bedrock, Vertex AI and Foundry the SDKs provide a client-side fallback middleware.
  • Plan for outages and rate limits with a second, pre-evaluated model — a different Claude tier, the same model through a different cloud, or another vendor behind your AI gateway.
  • Keep prompts portable. Model-specific tricks age badly; clear instructions, examples and schemas transfer.

Running your own selection#

  1. Write down the route: input, output, quality bar, latency budget, monthly volume, data classification.
  2. Build an evaluation set of 50–200 real examples with expected outputs or grading rubrics (evaluation methodology).
  3. Sweep two or three models × two or three effort levels. Record quality, p50/p95 latency and cost per successfully completed task (retries and human fixes included), not cost per request.
  4. Pick the cheapest cell that clears the bar, keep the runner-up as fallback, and store both in configuration.
  5. Re-run on every new model release. The sweep is cheap once the harness exists.

Common mistakes#

Common mistakeChoosing by vibes from a chat window

A model that impresses in a few chats can fail on your edge cases. Decide with an evaluation set and the real prompt, tools and context.

Common mistakeMaximum effort everywhere

Higher effort means more tokens and latency. Chat, classification and high-volume routes usually do well at low; measure before raising a default.

Common mistakeCopying prompts written for older models

Prompts tuned for older, weaker models are often over-prescriptive (“ALWAYS…”, “think step by step”, long rule lists) and can reduce quality on current models. Re-test and simplify when you upgrade.

Common mistakeIgnoring the migration notes

New models change API behaviour, not just quality — for example, current models reject assistant-message prefill, forced tool choice on some models, and fixed thinking budgets. Read the migration guide before switching a model ID in production.

Review questions#

How do you choose between Opus and Sonnet for a new feature? Start with the task: long multi-step reasoning and agentic loops favour Opus; well-specified, high-frequency work favours Sonnet. Then sweep both at two effort levels on an evaluation set and pick the cheapest configuration that clears the quality bar, measured as cost per completed task.

What is the effort parameter and when would you lower it? A per-request setting from low to max controlling how thoroughly the model thinks, calls tools and writes. Lower it for chat, classification, sub-agents and latency-sensitive routes; raise it only when evaluation shows quality headroom.

Why might one capable model at low effort beat a cascade of models? Newer models at low effort often match older or smaller models at high effort; a single model is simpler to operate and keeps one prompt-cache namespace, whereas a cascade pays to miss the cache on each hop.

How should an application handle a refusal? Check stop_reason before reading content; on refusal, use the server-side or client-side fallback, or return a clear message and log the category for review.

Summary#

  • Four current tiers: Fable 5.1 (hardest), Opus 5.5 (default for serious work), Sonnet 5.5 (everyday), Haiku 5.5 (high volume).
  • Choose tier and effort per route; measure cost per completed task on your own data.
  • Use caching, batches and fast mode deliberately; read limits from the Models API.
  • Keep model IDs in configuration, handle refusals, and keep a tested fallback.
