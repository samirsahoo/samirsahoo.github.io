On-Premise and Hybrid GenAI Deployment

Where GenAI should run — public API, cloud-managed, sovereign cloud, on-premise or air-gapped — and how to design a hybrid platform: data-classification routing, security, data privacy, GPU capacity and TCO, governance, and integration with existing enterprise systems.

Simple definition#

Deployment topology decides where each part of a GenAI system runs: the model, the retrieval index, the orchestration code and the logs. On-premise means inference runs on hardware you operate; hybrid means some workloads run on your hardware or private cloud and others call cloud-hosted models, with one control plane deciding which request goes where.

The architect’s job is not to pick “cloud” or “on-prem” once. It is to make the choice per data class and per workload, and to make that choice enforceable.

Why it matters#

Five drivers push enterprises away from “call the public API for everything”:

Driver Typical source
Data sovereignty and residency GDPR transfer rules, banking secrecy, public-sector and defence classification, customer contracts
Regulatory operational resilience EU DORA, PRA/EBA outsourcing rules: concentration risk, exit plans, audit rights over critical third parties
Cost at high steady volume Per-token pricing loses to amortised GPUs once utilisation is high and predictable
Latency and availability Plant floors, branches, ships, field devices; no dependency on internet links
Control and customisation Fine-tuned open-weight models, pinned versions, no surprise model deprecations

And three forces pull the other way: frontier quality (still mostly API-only), zero GPU operations, and speed of adoption. Hybrid exists because both lists are true at the same time.

The deployment spectrum#

Option Data path Model choice You operate Best for
Public API Leaves your network over TLS; contractual retention terms Full frontier range Nothing but the client Public and internal data, prototypes
Cloud-managed, private networking Stays in your cloud tenancy and region; private link, no internet Frontier + hosted open-weight, per-region availability IAM, networking, quotas Most confidential enterprise workloads
Dedicated capacity As above, with reserved, isolated throughput Usually a subset Capacity planning Predictable latency at steady volume
Sovereign cloud Local legal entity and operations Narrower catalogue, often lagging As above Public sector, regulated sectors with jurisdiction rules
On-premise Never leaves your data centre Open-weight only (plus some vendors’ licensed on-prem offerings) GPUs, drivers, serving stack, scaling, upgrades Restricted data, very high volume, fine-tuned models
Air-gapped No external connectivity at all Open-weight, imported through a controlled transfer Everything, including offline updates and evaluation Defence, critical infrastructure, classified data
Edge / on-device Stays on the device Small models (1–8B, quantized) Fleet distribution Offline field work, low latency, privacy on device

Key conceptThe quality gap is real but narrowing

Open-weight models run on-premise are close to mid-tier proprietary models for RAG, extraction, summarisation and classification. The gap is widest for hard multi-step reasoning and long-horizon agentic work. Put the hard tasks where the best models are allowed, and the sensitive high-volume tasks where your data is allowed.

Choosing per workload#

Questions that settle most cases:

  1. What is the most sensitive data that can reach the model — including retrieved documents, tool results and conversation history, not just the user’s question?
  2. Does the task need frontier reasoning, or does a 30–70B open-weight model pass your evaluation set?
  3. What is the steady and peak token volume, and how predictable is it?
  4. What does the regulator or customer contract require: region, jurisdiction, audit rights, exit plan?
  5. Can your organisation operate GPUs 24×7 — skills, on-call, hardware supply?

Hybrid reference architecture#

The defining component of a hybrid platform is an AI gateway that routes by data classification, not just by cost. Applications call one endpoint; the gateway decides which deployment is allowed to see the request.

Data-classification routing#

Data class Examples Allowed inference targets Extra controls
Public Marketing copy, public docs Any approved target Standard logging
Internal Policies, internal wiki Public API with enterprise terms, cloud-managed, on-prem Zero data retention where offered
Confidential Customer records, contracts, source code Cloud-managed in-region with private networking, on-prem PII redaction or pseudonymisation, encrypted logs, DPIA
Restricted Payment data, health data, trading strategy, M&A On-prem or sovereign only No prompt logging or masked logging, named-user access, approvals
Secret / classified Defence, national security Air-gapped only Physical and personnel controls

How the gateway knows the class:

  • Declared by the caller: each application is registered with a maximum data class; the gateway rejects calls above it.
  • Derived from the data: the retrieval layer stamps each chunk with its source classification; the highest class in the assembled prompt wins.
  • Detected: DLP or PII classifiers on the prompt catch what the first two miss. Detection is a safety net, not the primary control.

Trade-offRoute by the context, not the question

“Summarise this account’s complaints” is a harmless question. The retrieved complaints are confidential. Classify the assembled prompt, including RAG context and tool results, or a public-API route will leak data that the question alone did not reveal.

Security#

Self-hosting moves responsibilities from the provider to you. Treat the model server as a high-value internal service.

Area Controls
Network Zero-trust segmentation; model servers reachable only from the gateway; private endpoints for cloud models; egress allow-lists so self-hosted models and agents cannot call the internet
Identity Workload identity (SPIFFE or cloud IAM) between gateway and model servers; end-user identity propagated for audit; no shared API keys in applications. See Agent identity
Model supply chain Download weights only from verified sources; prefer safetensors over pickle formats that can execute code; verify hashes and signatures; scan model files; record each model in an AI-BOM; review licences
Serving stack Hardened, minimal container images; pinned CUDA, driver and serving-engine versions; patch cadence for CVEs in inference servers and their web front ends
Isolation Separate GPU pools or GPU partitioning (for example NVIDIA MIG) between tenants or data classes; no shared KV or prefix cache across trust boundaries
Data at rest Encrypt weights, vector indexes, prompt logs and fine-tuning datasets; keys in HSM/KMS; fine-tuned weights are as sensitive as their training data
Confidential computing Optional: TEEs and GPU confidential-computing modes protect data in use from the host operator — relevant for sovereign and multi-party scenarios
Application-layer threats Unchanged by location: prompt injection, excessive agency and output handling apply on-prem too. See AI security

Common mistake“It’s on-prem, so it’s secure”

On-premise removes third-party data exposure. It does not remove prompt injection, over-privileged tools, leaky logs or a vulnerable inference server. Many self-hosted model servers have been found exposed without authentication on internal and even public networks.

Data privacy#

Concern Design response
Residency and transfers Pin cloud models to in-region endpoints; check that cross-region inference or failover is switched off or approved; document transfer mechanisms
Provider retention and training Enterprise terms with zero data retention where available and no training on your data; verify abuse-monitoring retention exceptions
Minimisation Send only the fields the task needs; redact or pseudonymise identifiers at the gateway and re-identify in the response if required
Prompt and trace logs Logs contain personal data: classify them, restrict access, set retention, mask by default for restricted classes
Vector stores Embeddings and chunks are derived personal data: carry source ACLs and classification; support deletion so the right to erasure reaches the index
Fine-tuning data Models can memorise training data; avoid personal data in fine-tuning sets or treat the resulting weights as personal data
Assessments DPIA for high-risk processing; records of processing; link to the AI governance artefacts

Scalability and capacity planning#

What limits a self-hosted model#

Self-hosted capacity is set by GPU memory and memory bandwidth, not CPU:

  • Weights ≈ parameters × bytes per parameter (FP16 = 2, FP8/INT8 = 1, INT4 ≈ 0.5).
  • KV cache grows with context length × concurrent sequences; it decides how many users fit.
  • Throughput depends on continuous batching; latency per user worsens as the batch grows.

See Inference, latency and cost for the mechanics.

Scaling patterns#

Pattern What it does
Autoscale on the right signal Scale model replicas on queue depth, KV-cache utilisation or tokens/s, not CPU; GPUs pegged at 100% are normal
Warm pools Loading a 70B model takes minutes; keep minimum replicas warm for interactive traffic; scale-to-zero only for batch
Multi-LoRA serving Serve many fine-tuned adapters on one base model instead of one GPU set per variant
Workload separation Separate interactive and batch pools; run batch overnight to raise utilisation
Cloud burst Overflow confidential-class traffic to in-region cloud models when on-prem is saturated — only if the class allows it
Model tiering Small models on-prem for classification, routing and guardrails; larger ones only where evaluation says they are needed
Disaggregated serving Advanced: separate prefill and decode onto different GPU pools to tune TTFT and throughput independently

TCO: when does on-prem pay off?#

Worked example — the internal RAG assistant from Inference, latency and cost: ~2.4 billion tokens per month, about $9,200/month on a mid-tier API before caching.

Illustrative on-prem costs for one 8-GPU inference server (enough for this load with a quantized 70B model):

Cost item Monthly (illustrative)
Hardware amortised over 3–4 years $6,000–9,000
Power, cooling, rack space $1,500–3,000
Platform and on-call engineering (share of a team) $8,000–15,000
Redundancy: a second server for availability doubles hardware and power
Total ≈ $20,000–35,000

At this volume the API is two to four times cheaper. The picture flips when volume grows 5–10×, when the same cluster serves many use cases at high utilisation, or when data rules forbid the API anyway. Do the calculation with your prices, utilisation and staffing; the most common error is leaving out people and redundancy.

Key conceptUtilisation decides the economics

An API charges for tokens you use. A GPU charges for hours that pass. On-prem wins only when the GPUs are busy most of the time — so consolidate use cases onto a shared platform rather than buying GPUs per project.

Governance#

Governance in a hybrid estate is mostly about knowing what runs where, and controlling change.

  • Model catalogue: every approved model with its licence, version, evaluation results, allowed data classes and allowed deployment targets. The gateway enforces it.
  • Version pinning and change control: on-prem you choose when to upgrade; in the cloud, track provider deprecation dates. Either way, a model change goes through the evaluation suite like a code change. See LLMOps.
  • Policy as code: data-class routing rules, quotas and guardrail settings in version control, reviewed and audited.
  • Audit trail: who called which model, with what data class, through which application, under which policy version.
  • AI inventory and risk tiering: every use case registered with its deployment target. See AI governance.
  • Third-party and concentration risk: for regulated firms, critical AI providers need exit plans and tested fallbacks — a hybrid platform with an on-prem or second-provider route is the exit plan.
  • FinOps: chargeback per team for tokens and GPU hours, so the on-prem vs cloud decision stays visible.

Integration with existing enterprise systems#

GenAI succeeds or fails on integration. The model is the easy part; the value sits in systems of record, documents and workflows that already exist.

Integration point Pattern Watch out for
Identity (IdP, SSO) OIDC to the gateway; propagate user identity to tools; SCIM for groups that drive retrieval permissions Agents acting with service accounts that bypass user entitlements
API management / ESB Expose systems of record to agents through existing API gateways, wrapped as MCP servers or tools Bypassing the API layer and letting agents hit databases directly
Event streaming Kafka or similar for asynchronous LLM jobs, document-change events into ingestion, and results back into workflows Synchronous LLM calls inside latency-critical transaction paths
Content repositories Connectors for SharePoint, Confluence, ECM and file shares that copy ACLs into the index Indexing content without permissions — the most common RAG data leak
Data platforms Lakehouse or warehouse as a governed source; CDC to keep indexes fresh; text-to-SQL only through a semantic layer Letting the model generate SQL against raw production schemas
Business workflows BPM, ITSM and case-management tools call GenAI as a step, with human tasks for approvals GenAI output written straight into systems of record without validation
Observability OpenTelemetry GenAI semantic conventions into existing APM and logging A separate AI-only monitoring silo nobody on call looks at
Security operations Gateway and guardrail events to the SIEM; AI incidents in the existing incident process Prompt logs with personal data shipped unmasked to the SIEM
Secrets and keys Provider keys and model-server credentials in Vault/KMS, rotated, never in application config Long-lived API keys copied into notebooks and pipelines
CI/CD and GitOps Prompts, policies, model versions and evaluation sets in Git; deployments through the existing pipelines Prompt changes made live in a vendor console with no review
Legacy and mainframe Reach through existing service layers or APIs; use GenAI for code understanding and documentation of legacy estates Screen-scraping 3270 terminals when an API exists; consider computer use only as a last resort

For Java estates, Spring AI makes the hybrid model practical: the same ChatClient code can target an on-prem OpenAI-compatible vLLM endpoint or a cloud-managed model, selected by configuration and the gateway.

Running it day to day#

On-prem inference is a product, not a project:

  • Upgrade cadence for models (quarterly evaluation of new open-weight releases), serving engines, GPU drivers and CUDA — tested together.
  • SLOs and on-call for TTFT, error rate and availability, with runbooks for GPU failures and out-of-memory events.
  • Capacity reviews monthly: utilisation, queueing, demand forecast, hardware lead times.
  • Disaster recovery: a second site or a cloud fallback for restricted workloads that cannot use the cloud is often needed — and expensive; decide it explicitly.

Common mistakes#

Common mistakeOne deployment model for everything

“Everything on-prem” sacrifices frontier quality and adoption speed; “everything via public API” blocks the restricted use cases with the most value. Classify data and route.

Common mistakeBuying GPUs before measuring demand

Hardware bought per project sits idle. Start with cloud-managed models, measure token volumes and evaluation results, then size a shared cluster.

Common mistakeClassifying only the user’s question

The retrieved context and tool results usually carry the sensitive data. Classify the assembled prompt.

Common mistakeIgnoring the people cost

TCO comparisons that count hardware but not platform engineers, on-call and redundancy make on-prem look several times cheaper than it is.

Common mistakeNo exit plan for the cloud provider

Regulators increasingly ask how a critical AI service continues if a provider fails or changes terms. A tested second route is the answer.

Review questions#

When would you deploy an LLM on-premise instead of using a cloud API? When data classification or regulation forbids the cloud route, when steady volume is high enough to keep GPUs busy, when the environment is offline or latency-critical, or when a fine-tuned open-weight model must be pinned and controlled — and only if the organisation can operate GPUs reliably.

What is a hybrid GenAI architecture? One control plane — usually an AI gateway with a policy engine and model catalogue — routing each request to an on-prem, private-cloud or public model according to data class, task difficulty, cost and availability, with shared identity, logging and governance.

How does the gateway know which model a request may use? The application’s registered maximum data class, classification metadata carried by retrieved chunks and tool results (highest class wins), and DLP detection as a safety net. The policy maps each class to allowed targets.

What changes in security when you self-host? You take on the model supply chain (verified, safe-format weights, AI-BOM), serving-stack hardening and patching, network isolation and egress control, GPU and cache isolation between tenants, and encryption of weights, indexes and logs. Application-layer threats such as prompt injection are unchanged.

How do you size an on-prem inference cluster? From peak tokens per second and context lengths: weights memory by parameter count and precision, KV-cache memory by context × concurrency, throughput from benchmarks of your serving engine on your prompts, plus headroom and redundancy. Then validate with a load test.

How do you compare the cost of on-prem and API inference? Monthly tokens × API price versus amortised hardware, power, space, platform staff, on-call and redundancy, adjusted for expected utilisation. On-prem wins only with high, predictable utilisation.

How do you integrate GenAI with existing enterprise systems safely? Through existing identity, API management and event infrastructure: SSO with propagated user identity, systems of record exposed as governed APIs or MCP tools, ACL-aware content connectors, asynchronous jobs over the event bus, validation and human approval before writes, and telemetry into existing APM and SIEM.

Summary#

  • Choose deployment per data class and workload, not once for the enterprise.
  • The hybrid platform’s core is a gateway that routes by the classification of the assembled prompt.
  • Self-hosting moves security, supply-chain and patching duties to you; it does not remove application-layer risks.
  • Treat prompts, logs, vector indexes and fine-tuned weights as personal data where they contain it.
  • GPU economics depend on utilisation; count people and redundancy in TCO.
  • Govern with a model catalogue, policy as code, version control and an exit plan.
  • Integrate through existing identity, API, event, observability and security systems.
