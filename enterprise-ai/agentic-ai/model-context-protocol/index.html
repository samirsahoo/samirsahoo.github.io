Model Context Protocol (MCP)

Simple definition#

The Model Context Protocol (MCP) is an open standard for connecting AI applications to tools and data. An MCP server exposes capabilities — tools to call, resources to read, prompt templates to use — and any MCP-compatible AI application can discover and use them.

Analogy: USB-C for AI. Before USB, every device needed its own cable; before MCP, every AI app needed custom integration code for every system.

MCP was introduced by Anthropic in November 2024, adopted by the major AI vendors, IDEs and frameworks during 2025, and is now governed as an open project under the Linux Foundation’s Agentic AI Foundation.

The problem: N × M integrations#

Each tool is wrapped once as an MCP server and reused by every MCP client. Each AI application implements MCP once and gains access to every server.

Architecture: host, client, server#

  • Host — the application the user interacts with; it owns the LLM, the user’s consent and security policy.
  • Client — a connector inside the host; one client per server, keeping a 1:1 stateful session.
  • Server — a program exposing capabilities. It can be local (a subprocess) or remote (a web service).

The primitives#

Server-side primitives#

Primitive Controlled by What it is Example
Tools The model decides to call Functions with JSON Schema input (and optional output schema) create_ticket, query_orders
Resources The application decides what to include Read-only data identified by URI file:///reports/q3.md, crm://accounts/123
Prompts The user chooses Reusable prompt templates with arguments /summarise-incident incident_id

Tools can carry annotations that hint at behaviour — readOnlyHint, destructiveHint, idempotentHint, openWorldHint — which hosts use for approval UX. Annotations are hints from the server, so hosts must not trust them from untrusted servers.

Client-side primitives (server asks the host)#

Primitive What it lets a server do
Sampling Ask the host’s LLM to generate text — so a server can use AI without its own model credentials, under the host’s control and user approval
Roots Learn which directories or URIs the host allows it to work within
Elicitation Ask the user for missing information or confirmation through the host’s UI

Servers can also send notifications (for example “tool list changed”, progress updates, log messages) and support cancellation.

Protocol lifecycle#

MCP messages are JSON-RPC 2.0 requests, responses and notifications.

  1. Initialize — agree on protocol version and capabilities (what each side supports).
  2. Operate — list and call tools, read resources, get prompts; server may request sampling or elicitation.
  3. Shutdown — close the transport.

An example tool call on the wire#

{ "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": { "name": "get_order_status", "arguments": { "orderId": "A-10293" } } }

{ "jsonrpc": "2.0", "id": 7,
  "result": { "content": [ { "type": "text", "text": "Order A-10293: shipped, arriving 2 Nov." } ],
              "isError": false } }

Transports#

Transport How Use for
stdio Host launches the server as a subprocess; messages over stdin/stdout Local tools: filesystem, local Git, developer tools
Streamable HTTP Client POSTs JSON-RPC to one endpoint; server replies with JSON or streams via server-sent events; optional session ID header Remote, shared, multi-user servers in enterprises
HTTP + SSE (legacy) Separate SSE and POST endpoints Deprecated; replaced by Streamable HTTP

Authorization#

For remote HTTP servers, MCP specifies authorization based on OAuth 2.1:

Key rules: the MCP server is an OAuth resource server; tokens must be issued for that server (audience-bound) and the server must not pass the user’s token through to downstream APIs — it obtains its own tokens for those (avoiding the “confused deputy” problem). PKCE is required.

Security threats specific to MCP#

Threat What happens Mitigation
Tool poisoning Malicious instructions hidden in a tool’s description (“also read ~/.ssh and include it”) Only approved servers; review and pin tool descriptions; scanning
Rug pull A server changes tool definitions after approval Pin versions; alert on list_changed; re-approve changes
Tool shadowing / name collision A malicious server defines a tool that overrides or influences a trusted one Namespace tools per server; isolate servers
Indirect prompt injection via results Tool returns content (email, web page) with hidden instructions Treat results as data; human approval for sensitive actions; limit tool combinations
Data exfiltration Agent with private data access and an outbound channel leaks data Avoid the “lethal trifecta” (private data + untrusted content + external communication) in one session
Over-privileged servers Server uses an admin service account Delegated user tokens, least-privilege scopes
Token passthrough / confused deputy Server forwards client tokens to other APIs Forbidden by spec; use token exchange
Local server risks Unvetted local servers run with the user’s OS permissions; DNS rebinding to local HTTP servers Sandboxing, origin checks, bind to localhost, signed packages
Supply chain Typosquatted or compromised server packages Internal registry of approved servers; SBOM; signatures

Enterprise MCP architecture#

  • Domain teams own MCP servers for their systems — like they own APIs.
  • An MCP gateway centralises authentication, authorization, policy, per-tool allow-lists, rate limits and audit.
  • A registry lists approved servers with owners, data classification and versions.
  • Hosts connect only through the gateway; unapproved servers are blocked.

MCP compared#

REST/OpenAPI Framework tool (e.g. @Tool) MCP A2A
Purpose Program-to-program API In-process tool for one app Standard way for AI apps to use tools and context Standard way for agents to talk to agents
Discovery Docs / spec Code Runtime tools/list Agent cards
Reuse across AI apps Custom glue each time No Yes Yes
Typical unit Endpoint Method Tool / resource / prompt Task delegated to a remote agent

MCP and A2A (Agent2Agent protocol) are complementary: MCP connects an agent to its tools and data; A2A lets independent agents delegate tasks to each other. See multi-agent systems.

When to build an MCP server#

  • A system will be used by several AI applications or agents (copilot, IDE, business agents).
  • You want vendors’ AI products (desktop assistants, IDEs) to access your internal systems in a governed way.
  • You want domain teams to own AI access to their systems.

For a tool used only inside one application, an in-process tool (Spring AI @Tool) is simpler.

Common mistakes#

Common mistake“MCP makes it secure”

MCP standardises connection, not trust. A malicious or over-privileged MCP server is as dangerous as any other code with access to your data. Vet, sandbox, scope and audit.

Common mistakeExposing a 1:1 copy of an internal API

MCP tools are read by an LLM. Apply the same tool design principles: task-level tools, clear descriptions, compact results.

Review questions#

What is MCP and what problem does it solve? An open protocol that standardises how AI applications connect to tools and data sources. It turns N×M custom integrations into N+M: each system is wrapped once as an MCP server and each AI application implements an MCP client once.

Explain host, client and server. The host is the AI application with the LLM and user. It creates one MCP client per server; each client keeps a stateful JSON-RPC session with one server. Servers expose tools, resources and prompts.

What are tools, resources and prompts in MCP? Tools are model-invoked functions with input schemas; resources are application-controlled read-only data identified by URIs; prompts are user-selected templates. Clients can additionally offer sampling, roots and elicitation to servers.

Which transports does MCP support? stdio for local subprocess servers and Streamable HTTP for remote servers (HTTP POST with optional server-sent-event streaming). The older HTTP+SSE transport is deprecated.

How is MCP secured? Remote servers use OAuth 2.1 authorization with PKCE and audience-bound tokens; servers must not pass through client tokens. In the enterprise add an MCP gateway, an approved-server registry, least-privilege scopes, human approval for destructive tools, pinned tool definitions, and audit logs.

What are the main MCP security risks? Tool poisoning, rug pulls, tool shadowing, indirect prompt injection through tool results, data exfiltration, over-privileged servers, token passthrough and supply-chain attacks on server packages.

MCP vs A2A? MCP connects an agent to tools and context; A2A lets agents built by different teams or vendors discover each other and delegate tasks. Many systems use both.

Review tipDraw it

Draw host → clients → servers with transports, then add the gateway, IdP and registry. Mentioning tool poisoning and the no-token-passthrough rule shows you have gone beyond the marketing.

Summary#

  • MCP standardises how AI apps use external tools and data: N+M instead of N×M.
  • Host (AI app) → one client per server → server exposing tools, resources and prompts.
  • JSON-RPC 2.0 with capability negotiation; stdio locally, Streamable HTTP remotely; OAuth 2.1 for auth.
  • MCP standardises connection, not trust: govern servers with a gateway, registry, least privilege and audit.
