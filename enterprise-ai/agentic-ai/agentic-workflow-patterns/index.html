Agentic Workflow Patterns

The building-block patterns of agentic systems with diagrams and examples: prompt chaining, routing, parallelization (sectioning and voting), orchestrator-workers, evaluator-optimizer, plan-and-execute, reflection, and human-in-the-loop — and how to choose.

Simple definition#

Agentic patterns are reusable shapes for combining LLM calls, tools and code — the “design patterns” of AI systems. Most production systems are a composition of a few of them. They range from fully code-controlled workflows to fully model-controlled agents.

1. Prompt chaining#

Break a task into fixed steps; each LLM call processes the previous output. Add gates (code checks) between steps.

  • Use when: the task decomposes cleanly into fixed sub-tasks.
  • Example: claim email → extract claim fields → validate → draft acknowledgement → translate.
  • Why it works: each call is simpler and testable; accuracy improves at the cost of latency.

2. Routing#

Classify the input, then send it to a specialised handler (prompt, model or workflow).

  • Use when: inputs fall into distinct categories that are better handled separately.
  • Benefits: specialised prompts, cheaper models for easy cases (see model routing).

3. Parallelization#

Run LLM calls simultaneously and combine results programmatically.

  • Sectioning — independent sub-tasks in parallel (speed, focus). Also: one call answers while another checks guardrails.
  • Voting — same task several times for confidence (security review, content moderation).

4. Orchestrator–workers#

A central LLM breaks a task into sub-tasks dynamically, delegates them to worker LLMs, and synthesises the results. Unlike sectioning, the sub-tasks are not known in advance.

  • Use when: the number and nature of sub-tasks depend on the input (research, multi-file code changes).
  • This is the basis of the supervisor pattern in multi-agent systems.

5. Evaluator–optimizer#

One LLM generates; another evaluates against criteria and gives feedback; repeat until good enough.

  • Use when: clear evaluation criteria exist and iteration measurably helps (translation nuance, SQL that must pass tests, policy-compliant marketing copy).
  • Use deterministic evaluators where you can: unit tests, schema validation, SQL EXPLAIN, linters.

6. Plan-and-execute#

The agent writes an explicit plan first, executes steps (often with a cheaper model or plain code), and re-plans when results differ from expectations.

  • Benefits: the plan is visible (users and reviewers can approve it), cheaper execution, better long-horizon behaviour.
  • Variants: ReWOO (plan all tool calls up front), LLMCompiler (plan a DAG of parallel calls).

7. Reflection#

The agent critiques its own output or failed attempts and stores lessons for the next try (Reflexion). Cheaper than a separate evaluator, but self-critique is less reliable than external checks — prefer real signals (test results, tool errors) as the input to reflection.

8. Human-in-the-loop (HITL)#

A pattern that combines with all others: pause at defined points for human approval, correction or input.

Requires durable state (checkpoints) so the agent can wait without holding a thread; see memory and state.

Choosing a pattern#

Situation Pattern
Fixed steps, each simpler than the whole Prompt chaining
Distinct input categories Routing
Independent sub-tasks, or need confidence Parallelization
Sub-tasks unknown until runtime Orchestrator–workers
Clear quality criteria, iteration helps Evaluator–optimizer
Long multi-step tasks needing a visible plan Plan-and-execute
Open-ended, path unknowable Autonomous agent (ReAct loop)
Risky or irreversible actions + Human-in-the-loop

Common mistakes#

Common mistakeStarting with a framework instead of the pattern

Frameworks hide prompts and control flow, making debugging hard. Understand the pattern; many can be implemented in a few dozen lines with a plain chat client.

Common mistakeLoops without exit criteria

Evaluator–optimizer and reflection loops need a maximum number of rounds and a definition of “good enough”.

Review questions#

What is the difference between prompt chaining and an agent? In prompt chaining, code defines a fixed sequence of LLM calls with checks between them. In an agent, the LLM decides the next step at runtime in a loop.

When would you use orchestrator–workers instead of parallel sectioning? When sub-tasks cannot be known in advance and depend on the input — the orchestrator plans them dynamically. Sectioning uses a fixed, predefined split.

Explain the evaluator–optimizer pattern. A generator produces output, an evaluator checks it against explicit criteria and returns feedback, and the generator revises — looping until criteria are met or a round limit is reached. Use deterministic evaluators such as tests where possible.

What is plan-and-execute and why use it? A planner produces an explicit multi-step plan, an executor runs steps with tools, and the planner re-plans when results deviate. It makes long tasks more reliable, visible and cheaper.

How do you implement human-in-the-loop in an agent? Define checkpoints for risky actions, persist the agent’s state, notify an approver with context, resume from the checkpoint after approval or edit, and log the decision.

Review tipCombine patterns out loud

A strong design composes patterns: “A router sends claims to specialised chains; complex claims go to an orchestrator–workers agent; refunds above €100 pause for human approval.”

Summary#

  • Patterns range from code-controlled (chaining, routing, parallelization) to model-controlled (orchestrator–workers, agents).
  • Evaluator–optimizer, plan-and-execute and reflection improve quality on hard tasks.
  • Human-in-the-loop adds safety to any pattern and needs durable state.
  • Choose the simplest pattern that meets requirements; compose patterns for real systems.
