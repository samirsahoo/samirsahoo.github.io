Evaluating RAG and LLM Applications

How to measure AI quality: golden datasets, retrieval metrics (recall@k, precision@k, MRR, nDCG), generation metrics (faithfulness, answer relevance, context precision and recall), LLM-as-judge, RAGAS-style frameworks, human review, and evaluation in CI and production.

Simple definition#

Evaluation is measuring how well your AI system does its job, on a fixed set of test cases, with repeatable scores. For RAG you measure two things separately: did we find the right information (retrieval), and did we use it correctly (generation)?

Key conceptNo evaluation, no engineering

Without numbers, every change to chunking, prompts or models is a guess. Evaluation turns AI development into normal engineering: change, measure, compare, decide.

What to evaluate#

The golden dataset#

A golden dataset (evaluation set) is a list of test cases:

Field Example
Question “Can contractors claim home-office equipment?”
Reference answer “No. Only employees on permanent or fixed-term contracts may claim, up to €500 per year.”
Relevant document/chunk IDs policy-equipment-2026#3.1
Metadata Category: HR; difficulty: medium; type: single-hop

How to build it:

  1. Start with real questions from users, support tickets, search logs or subject-matter experts.
  2. Cover the space — easy and hard, single- and multi-hop, every major document type, questions with no answer in the corpus, adversarial inputs.
  3. Synthetic generation — an LLM generates question–answer pairs from chunks; experts review a sample. Fast for coverage, but check realism.
  4. Size — 50–100 cases to start, growing to several hundred. Add every production failure.
  5. Version it like code.

Retrieval metrics#

Given the known relevant chunks for each question:

Metric Question it answers Formula, simply
Recall@k Did the relevant chunks appear in the top k? relevant found in top k ÷ total relevant
Precision@k How much of the top k is relevant? relevant in top k ÷ k
Hit rate@k Was at least one relevant chunk in the top k? % of questions with a hit
MRR (mean reciprocal rank) How high is the first relevant result? average of 1 ÷ rank of first relevant
nDCG@k Are the most relevant results at the top? rank-weighted gain, normalised to the ideal order

Example. Relevant chunk found at rank 3 → reciprocal rank 1/3. Over three questions with first-hit ranks 1, 3 and “not found”: MRR = (1 + 0.33 + 0) / 3 = 0.44.

Recall@k is the most important for RAG: if the right chunk is not retrieved, nothing downstream can fix it.

Generation metrics#

Metric What it measures How it is computed
Faithfulness / groundedness Are the answer’s claims supported by the retrieved context? (hallucination check) LLM splits the answer into claims and checks each against the context
Answer relevance Does the answer address the question? LLM judge, or similarity between the question and questions generated from the answer
Context precision Are the relevant chunks ranked at the top? LLM or labels judge each retrieved chunk
Context recall Does the context contain everything needed for the reference answer? Check reference-answer claims against context
Answer correctness Does it match the reference? LLM judge or semantic similarity to reference
Citation accuracy Do citations point to sources that support the sentence? Rule check + LLM judge
Format / policy compliance Length, tone, required disclaimers, no PII Rules, regex, classifiers

These are the metrics implemented by frameworks such as RAGAS, DeepEval, TruLens, Arize Phoenix, LangSmith and Langfuse. Spring AI has RelevancyEvaluator and FactCheckingEvaluator for tests; see Spring AI in production.

LLM-as-a-judge#

Using a strong LLM to grade outputs against a rubric. It scales human-like judgement to thousands of cases. Judges have known biases — position, verbosity, self-preference — covered in evaluation methodology.

Make judges reliable:

  • Specific rubrics — “Score 1 if every claim is supported by the context, else 0”, not “rate quality 1–10”.
  • Binary or small scales with explanations before the score.
  • Calibrate — compare judge scores with expert labels on 50–100 cases; aim for high agreement.
  • Known biases — position bias (prefers first option), verbosity bias (prefers longer), self-preference (prefers its own model family). Mitigate with swapped order, length-neutral rubrics and a different model family as judge.
  • Pairwise comparison (A vs B) is often more reliable than absolute scores when comparing versions.

Evaluation in the lifecycle#

Also run A/B tests for business outcomes (resolution rate, time saved, customer satisfaction) — the metrics that justify the investment.

Human evaluation#

Automated metrics do not replace experts for high-stakes domains. Use human review to build the golden dataset, calibrate judges, review samples of production traffic, and sign off releases for regulated use cases. Keep review guidelines written and consistent.

Common mistakes#

Common mistakeOnly measuring the final answer

When the score drops you will not know if retrieval or generation broke. Measure both.

Common mistakeTrusting an uncalibrated judge

An LLM judge with a vague rubric produces confident, inconsistent numbers. Calibrate against human labels.

Common mistakeA static dataset

Users ask new questions and documents change. Grow the dataset from production failures and refresh references when sources change.

Review questions#

How do you evaluate a RAG system? Build a golden dataset of real questions with reference answers and relevant chunk IDs. Measure retrieval (recall@k, MRR, nDCG) and generation (faithfulness, answer relevance, correctness, citation accuracy) separately, using LLM-as-judge calibrated against human labels. Run it in CI on every change, and monitor sampled production traffic online with user feedback.

What is faithfulness? Whether every claim in the answer is supported by the retrieved context — the main hallucination metric for RAG. It is computed by splitting the answer into claims and verifying each against the context.

What is the difference between context precision and context recall? Context precision asks whether retrieved chunks are relevant and ranked at the top. Context recall asks whether the retrieved context contains all the information needed for the reference answer.

What are the risks of LLM-as-a-judge? Position, verbosity and self-preference biases, inconsistent scoring with vague rubrics, and cost. Mitigate with precise binary rubrics, explanations, order swapping, a different model family, and calibration against human labels.

How do you prevent regressions when changing a prompt or model? Version prompts and datasets, run the evaluation suite in CI against the current baseline, block on drops in key metrics, roll out with canaries, and monitor online.

Review tipName metrics and the process

Listing RAGAS metrics is good; explaining how the dataset is built, how judges are calibrated and how evaluation gates releases is what distinguishes a mature evaluation practice.

Summary#

  • Evaluate retrieval and generation separately, plus end-to-end correctness and business outcomes.
  • Retrieval: recall@k, precision@k, MRR, nDCG. Generation: faithfulness, answer relevance, context precision/recall, citation accuracy.
  • LLM-as-judge scales evaluation; calibrate it and control its biases.
  • Run offline evaluation in CI and online evaluation on production samples; turn failures into test cases.
