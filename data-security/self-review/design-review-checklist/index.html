Design Review Checklist

A repeatable checklist for reviewing event-driven, data and security designs: ten review areas with questions and red flags, a 0–3 scoring rubric and a one-page review template.

How to use it#

Use this checklist to review your own design before building, or a team’s design at an architecture board. Score each area 0–3 and record the evidence.

1. Goals and non-functional requirements#

  • Throughput (average and peak), latency budgets, availability, RPO and RTO stated per flow?
  • Which flows are synchronous (the user waits) and which are asynchronous?
  • Red flags: “real-time” undefined; no peak numbers; one SLO for everything.

2. Boundaries and data ownership#

  • Each piece of data has one owning service? No shared databases between services?
  • Do data that must change together live together?
  • Red flags: services reading each other’s tables; every change spans services.

3. Events and contracts#

  • Events named as past-tense facts; integration events separated from internal ones?
  • Keys chosen for ordering; partition count sized for growth?
  • Schemas registered, compatibility mode chosen (transitive if replayed), CI checks in place?
  • No secrets or unnecessary PII in events; trace context propagated?
  • Red flags: schemaless JSON; compatibility NONE; low-cardinality keys; PAN in events.

4. Consistency#

  • Consistency model stated per operation (strong where invariants live, eventual elsewhere)?
  • Invariants protected inside one ACID or consensus boundary?
  • Read-your-writes handled where users need it?
  • Red flags: decisions made on async replicas or read models; “eventually consistent” used as an excuse.

5. Failure handling#

  • Outbox (or equivalent) for state plus event; idempotent consumers; idempotency keys on APIs?
  • Sagas with explicit compensations, timeouts and manual-review paths?
  • Retries with backoff, DLTs, poison-message handling; the timeout (unknown) outcome designed?
  • Reconciliation jobs for money and critical data?
  • Red flags: @Transactional around remote calls; infinite retries; no compensation design.

6. Data platform and governance#

  • Open table formats and one catalog; medallion or product layers defined?
  • Owners, contracts and quality gates per data product; lineage captured automatically?
  • Regulatory reports traceable to source (BCBS 239)?
  • Red flags: copies per tool; no owners; quality checks only on final reports.

7. Data security and privacy#

  • Data classified; sensitive identifiers tokenised early; masking by default?
  • Encryption in transit and at rest with managed keys (HSM/KMS); key separation of duties?
  • ABAC or row and column security; JIT access to restricted data; access recertification?
  • Residency, retention and erasure (including immutable stores) designed?
  • Red flags: production data in test; PII in logs and prompts; “we encrypt the disk” as the only control.

8. Threats and security architecture#

  • Current threat model (DFD, trust boundaries, STRIDE, LINDDUN for personal data)?
  • Zero trust: strong user and workload identity, mTLS, per-object authorisation?
  • Supply chain: SBOM, signing, provenance, admission policy; secrets dynamic and short-lived?
  • Crypto inventory and crypto-agility for PQC?
  • Red flags: trusted internal network; authorisation only at the gateway; long-lived static credentials.

9. AI risk#

  • AI use cases inventoried and classified (EU AI Act tier)?
  • Least agency, user-scoped tools, human approval for consequential actions?
  • Permission-aware RAG; output validation; token and cost limits?
  • Red-teamed and continuously evaluated; traces kept?
  • Red flags: agents with service-account superpowers; security rules only in the system prompt.

10. Compliance and operations#

  • Applicable regulations listed (PCI DSS, DORA, PSD2/3, GDPR/DPDP, RBI, CERT-In, SEBI, AI Act); controls mapped once to many?
  • Incident detection, classification and reporting clocks (4/6/24/72 h) automated and rehearsed?
  • Resilience testing, restore tests, third-party register and exit plans?
  • Monitoring: lag, DLTs, saga states, quality, access anomalies, cost?
  • Red flags: compliance as an annual project; paper-only incident plans; unknown ICT dependencies.

Scoring rubric#

Score Meaning
0 Not considered
1 Considered, but not designed
2 Designed, but not yet verified
3 Designed and verified (tests, evidence, drills)

A design is ready to build at an average of at least 2 with no zeros in areas 4, 5, 7 or 8. It is ready for production at 3 in all applicable areas.

Quick check#

Which four areas must not score zero before building? Consistency, failure handling, data security and privacy, and threats and security.

What does a score of 3 require? The area is designed and verified with evidence: tests, drills or audits.
