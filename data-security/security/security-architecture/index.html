Security Architecture: Zero Trust, AppSec, Supply Chain and Cryptography

The core of enterprise security architecture: defence in depth and zero trust (NIST SP 800-207), identity for people and workloads, OWASP Top 10:2025 and API security, secure SDLC and software supply chain (SLSA, SBOM, Sigstore), secrets, cryptography and post-quantum readiness, detection and response, NIST CSF 2.0 and security for event and data platforms.

Simple definition#

Security architecture is the set of principles, patterns and controls that make a system resist, detect and recover from attacks by design. It covers identity, network, application, data, supply chain, cryptography and operations.

Core principles#

Principle Meaning
Defence in depth Multiple independent layers, so one failure is not a breach
Least privilege Minimum access, for minimum time
Zero trust Never trust by network location; verify explicitly every time
Secure by default Safe settings out of the box; insecure options require effort
Fail securely Errors deny access. This is OWASP A10:2025, “Mishandling of Exceptional Conditions”.
Assume breach Limit blast radius; detect and respond fast
Separation of duties No single person or service can complete a critical action alone
Economy of mechanism Simple designs are easier to verify

Zero trust architecture#

NIST SP 800-207 defines zero trust as moving defences from static network perimeters to users, assets and resources. Every request is authenticated, authorised and encrypted, based on identity and context.

Building blocks:

  • Strong identity: phishing-resistant MFA (FIDO2 passkeys) for people. Workload identity (SPIFFE/SPIRE, cloud workload identity, Kubernetes service accounts with OIDC federation) for services, with no long-lived secrets.
  • Device posture (managed, patched, EDR running).
  • Micro-segmentation: service mesh mTLS with authorisation policies, network policies, private endpoints.
  • ZTNA replaces VPNs for user access to applications.
  • Continuous evaluation: sessions re-evaluated on risk changes.
  • The CISA Zero Trust Maturity Model (identity, devices, networks, applications and workloads, data) helps plan the journey.

Application security: OWASP Top 10:2025#

# Category (2025) Notes
A01 Broken Access Control Still #1; now includes SSRF
A02 Security Misconfiguration Cloud and framework defaults, verbose errors
A03 Software Supply Chain Failures New/expanded: dependencies, build systems, distribution
A04 Cryptographic Failures Weak or missing encryption, bad key handling
A05 Injection SQL, NoSQL, OS command, LDAP, and template injection
A06 Insecure Design Missing threat modelling and secure patterns
A07 Authentication Failures Credential stuffing, weak sessions
A08 Software or Data Integrity Failures Unsigned updates, insecure deserialisation
A09 Security Logging and Alerting Failures Cannot detect or investigate
A10 Mishandling of Exceptional Conditions New: failing open, leaking errors, unsafe recovery

Also use the OWASP API Security Top 10 (2023). Its top item, BOLA (broken object-level authorisation: changing /accounts/123 to /accounts/124), is the most common API breach cause. Check authorisation per object on every request.

API security patterns: OAuth 2.0 / OIDC with short-lived tokens; FAPI 2.0 for financial APIs (sender-constrained tokens via mTLS or DPoP, PAR); schema validation at the gateway; rate limiting; no sensitive data in URLs; consistent error handling.

Secure SDLC and DevSecOps#

  • SAST (static analysis), SCA (dependency vulnerabilities and licences), secrets scanning, IaC scanning, container scanning, DAST and API testing.
  • Frameworks: NIST SSDF (SP 800-218), OWASP SAMM, BSIMM.
  • Security champions in each team; findings triaged by exploitability and reachability, not raw counts.

Software supply chain security#

Control What it does
SBOM (CycloneDX, SPDX) Inventory of components for every artifact; feeds vulnerability response
SLSA (v1.x) Build integrity levels: provenance, hardened build platforms
Signing (Sigstore cosign, keyless with OIDC) Prove who built the artifact; verify at deploy
Provenance attestations (in-toto) Prove how and from what source it was built
Dependency hygiene Pinned versions, private mirrors, typosquatting checks, OpenSSF Scorecard
Admission policy Only signed, attested, scanned images run (Kyverno, Gatekeeper)

Regulation now pushes this: the EU Cyber Resilience Act (vulnerability reporting obligations from September 2026, full application from December 2027) and US federal secure software attestation requirements.

Secrets management#

  • No secrets in code, images or Git. Use Vault / OpenBao, cloud secret managers, or the External Secrets Operator.
  • Prefer dynamic, short-lived credentials (database credentials issued per session) and workload identity federation over static keys.
  • Rotate automatically; detect leaks with pre-commit hooks and repository scanning.

Cryptography and post-quantum readiness#

  • Use vetted libraries and modern defaults: TLS 1.3, AES-GCM or ChaCha20-Poly1305, Ed25519 or ECDSA P-256, SHA-256+, Argon2id or bcrypt for passwords.
  • Post-quantum cryptography (PQC): NIST published FIPS 203 (ML-KEM), FIPS 204 (ML-DSA) and FIPS 205 (SLH-DSA) in August 2024, and selected HQC as a backup KEM in 2025. The threat is “harvest now, decrypt later” for long-lived secrets, which is exactly what financial data is.
  • What to do now:
    1. Build a cryptographic inventory (CBOM).
    2. Design crypto-agility (algorithms configurable, not hard-coded).
    3. Adopt hybrid key exchange (X25519 + ML-KEM) in TLS where supported; major browsers and CDNs already use it.
    4. Follow regulator timelines. The EU roadmap targets starting the transition by 2026 and protecting critical infrastructure by around 2030. US NSA CNSA 2.0 sets migration milestones from about 2027 to 2033.

Detection and response#

  • Logging: centralised, tamper-evident, with useful context (who, what, where, result). Never log secrets or full PANs.
  • SIEM + SOAR, EDR/XDR, cloud detection, UEBA for insider threats.
  • Detection engineering mapped to MITRE ATT&CK; purple-team exercises.
  • Incident response plans with regulatory clocks built in: DORA (initial notification within 4 hours of classifying as major, and no later than 24 hours from awareness), CERT-In (6 hours), RBI (6 hours via its reporting platform), GDPR (72 hours to the supervisory authority).

Framework Use
NIST CSF 2.0 Govern, Identify, Protect, Detect, Respond, Recover; the 2024 version added Govern
ISO/IEC 27001:2022 Certifiable information security management system (93 Annex A controls)
CIS Controls v8.1 Prioritised technical safeguards
NIST SP 800-53 Detailed control catalogue
Cloud Security Alliance CCM Cloud controls mapping

Securing event and data platforms#

  • Kafka: TLS and mTLS, SASL/OAUTHBEARER with short-lived tokens, ACLs per principal and topic (producers can write only their topics), encryption at rest, quotas, audit logs. Consider client-side field encryption for sensitive payloads, and no PII in keys or headers.
  • Databases: private networking, IAM authentication, least-privilege roles, encryption with customer-managed keys, activity monitoring.
  • Lakehouse: catalog-enforced ABAC, masking, row filters, audited access. See data security.

Common mistakes#

Common mistakeTrusting the internal network

Lateral movement after one compromise is how most breaches grow. Authenticate and authorise every hop.

Common mistakeChecking authorisation only at the UI or gateway

APIs called directly bypass it, which leads to BOLA. Check object-level authorisation in the service.

Common mistakeUnsigned artifacts and unpinned dependencies

Supply chain attacks bypass every runtime control. Sign, attest, pin and verify at admission.

Common mistakeHard-coded crypto

PQC migration will be painful. Inventory crypto and make algorithms configurable now.

Quick check#

What is zero trust in one sentence? Never grant access based on network location. Verify identity, device and context explicitly for every request, with least privilege.

What changed in OWASP Top 10:2025? Software Supply Chain Failures (A03) and Mishandling of Exceptional Conditions (A10) are new, and SSRF was folded into Broken Access Control.

What is BOLA? Broken object-level authorisation: an API does not check that the caller may access the specific object ID requested.

What do SBOM, SLSA and Sigstore each provide? An SBOM is a component inventory. SLSA defines build integrity levels and provenance. Sigstore provides artifact signing and verification.

Why start post-quantum migration now? Harvest-now-decrypt-later: data with long confidentiality needs can be captured today and decrypted later. Migration takes years, so start with an inventory, crypto-agility and hybrid TLS.

What function did NIST CSF 2.0 add? Govern.

Summary#

  • Layer defences, use least privilege, assume breach, and verify every request (zero trust).
  • Design against the OWASP Top 10:2025 and API Top 10, and check authorisation per object.
  • Secure the supply chain with SBOMs, SLSA provenance, signing and admission policy.
  • Manage secrets dynamically, inventory crypto for the PQC transition, and build detection with regulatory clocks.
