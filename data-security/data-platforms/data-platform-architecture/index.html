Modern Data Platform Architecture

How modern data platforms are built: warehouse vs lake vs lakehouse, open table formats (Apache Iceberg v3, Delta Lake, Hudi), catalogs (Polaris, Unity Catalog), medallion layers, batch and streaming ingestion, query engines, data mesh and data products, and platforms for AI.

Simple definition#

A data platform collects data from operational systems, stores it reliably and cheaply, and turns it into trusted data products for reporting, analytics, machine learning and AI. The modern default is a lakehouse: open table formats on object storage, queried by many engines under one governance catalog.

The problem#

Operational databases are built for transactions, not for analysis across years and systems. Historically, companies copied data into warehouses (fast and governed but expensive and closed) and lakes (cheap and flexible but often a “data swamp”). The duplication brought inconsistent numbers, high cost and a separate security model per copy.

Warehouse vs lake vs lakehouse#

Data warehouse Data lake Lakehouse
Storage Proprietary, managed Files on object storage Open table formats on object storage
Data Structured Any Any, with tables on top
Transactions Yes No Yes (ACID via table format)
Engines One Many, ungoverned Many, through one catalog
Strength BI performance, governance Cost, ML, raw data Both, without copies

Open table formats#

A table format adds database features to files: ACID commits, schema evolution, time travel, partition evolution and row-level updates.

Apache Iceberg Delta Lake Apache Hudi
Origin Netflix → Apache Databricks → Linux Foundation Uber → Apache
Strength Engine-neutral, hidden partitioning, REST catalog standard Deep Spark and Databricks integration Upserts and incremental processing
Ecosystem (2026) Broadest multi-vendor support (Snowflake, AWS S3 Tables, BigQuery, Databricks, Trino, Flink, Spark, DuckDB) Databricks, Fabric, with UniForm Iceberg compatibility Streaming-heavy upsert workloads

Iceberg format v3 (spec finalised in 2025, with engine support rolling out through 2026) adds:

  • Deletion vectors: compact bitmaps in Puffin files that mark deleted rows, so updates and deletes are faster.
  • Row lineage: a stable row ID and a last-updated sequence number per row, for incremental processing and CDC.
  • The VARIANT type for semi-structured data; geometry and geography types; nanosecond timestamps; default column values; and multi-argument transforms.

A commit atomically swaps the catalog pointer to new metadata. Readers see a consistent snapshot, and time travel reads older snapshots.

Catalogs: the control point#

The catalog tracks tables and, increasingly, enforces governance for every engine.

  • Iceberg REST Catalog is the open API standard used by most engines.
  • Apache Polaris is an open-source Iceberg REST catalog, originally from Snowflake.
  • Unity Catalog (open-sourced by Databricks) covers tables, volumes, models and functions, with access control and lineage.
  • AWS Glue / S3 Tables, Google BigLake and Microsoft OneLake are cloud catalogs.

Key conceptGovern in the catalog, not per engine

When Spark, Trino, Flink, Snowflake and Python all read the same Iceberg table through one catalog, access policies, masking and lineage can be enforced once. See data security.

Medallion layers#

Layer Content Rules
Bronze (raw) Data as received from CDC, events and files; append-only Keep the source fidelity; add ingestion metadata; restricted access
Silver (conformed) Cleaned, de-duplicated, typed, joined to reference data; PII tokenised Quality checks; standard keys and types
Gold (products) Business-level aggregates and data products (customer 360, daily positions, regulatory datasets) Contracts, SLOs, owners, documentation

Ingestion: batch, CDC and streaming#

  • CDC (Debezium, cloud DMS, Fivetran, Airbyte) from OLTP databases into bronze.
  • Streaming: Kafka → Flink, or Kafka Connect Iceberg sink → Iceberg, with commits every few seconds to minutes. This is a “streaming lakehouse”.
  • Batch files and APIs for partner and legacy data.
  • Zero-ETL integrations (operational DB → warehouse or lakehouse managed by the cloud) reduce pipeline code. Check what transformations and governance you lose.
  • Orchestrate with Apache Airflow 3, Dagster or cloud equivalents; transform with dbt or SQLMesh, or Spark and Flink jobs.

Query and serving engines#

Need Engines
Large transformations Apache Spark, Flink (batch mode), dbt on a warehouse
Interactive SQL Trino / Starburst, Snowflake, BigQuery, Databricks SQL, Dremio
Local and embedded analytics DuckDB
Real-time OLAP (sub-second on fresh data) Apache Pinot, ClickHouse, Apache Druid, StarRocks
ML and AI Spark ML, Ray, feature stores (Feast), vector search

Data mesh and data products#

Data mesh (Zhamak Dehghani) has four principles:

  1. Domain ownership: the payments domain owns payments data.
  2. Data as a product: discoverable, addressable, trustworthy, self-describing, interoperable, secure.
  3. Self-serve data platform: a platform team provides the lakehouse, catalog, pipelines and governance as a service.
  4. Federated computational governance: global rules (classification, interoperability, privacy) automated in the platform; domains decide locally.

A data product bundles data, code, metadata, a contract, SLOs, an owner and access policies. Most enterprises adopt a hybrid: a central platform with domain-owned data products.

Data platforms for AI#

  • Unstructured data (documents, emails, call transcripts) is governed in the same catalog: volumes, document tables, embeddings.
  • Feature stores give consistent features for training and serving.
  • Vector search inside the lakehouse or in a vector database, with the same access policies as the source documents.
  • Lineage from source to model to prediction for AI governance. See AI security and the EU AI Act in FinTech regulations.

Common mistakes#

Common mistakeA lake without a catalog or contracts

It becomes a data swamp. Register every table, assign owners and enforce quality at the silver and gold layers.

Common mistakeCopying data into every tool

Each copy has its own security, cost and numbers. Use open formats and one catalog; bring engines to the data.

Common mistakeData mesh as a reorganisation only

Without a self-serve platform and automated governance, every domain builds its own silo.

Common mistakeRaw PII in silver and gold

Tokenise or mask at ingestion so most consumers never see raw identifiers.

Quick check#

What makes a lakehouse different from a data lake? Open table formats add ACID transactions, schema evolution and time travel on object storage, and one catalog governs access for many engines.

Name three Iceberg v3 features. Deletion vectors, row lineage, the VARIANT type, geospatial types, nanosecond timestamps and default values.

What are the medallion layers? Bronze (raw, as received), silver (cleaned, conformed, tokenised) and gold (business-level data products).

What are the four data mesh principles? Domain ownership, data as a product, a self-serve platform, and federated computational governance.

Why does the catalog matter for security? It is the one place to enforce access, masking and lineage for every engine reading the same tables.

Summary#

  • Lakehouse = open table formats on object storage plus one catalog plus many engines.
  • Iceberg is the most engine-neutral format; v3 adds deletion vectors, row lineage and VARIANT.
  • Medallion layers organise quality. Data products give ownership and contracts.
  • Govern in the catalog, and extend the same platform to AI data.
