Service Mesh: Istio, Linkerd, Cilium and Ambient Mode

What a service mesh adds — mTLS, traffic management, resilience and telemetry — sidecar vs sidecarless (Istio ambient with ztunnel and waypoints, Cilium), how to choose Istio, Linkerd or Cilium, and when you do not need a mesh.

Simple definition#

A service mesh is an infrastructure layer that handles service-to-service communication for you: encrypts it with mutual TLS, applies traffic rules (retries, timeouts, canary weights), enforces identity-based authorisation, and emits telemetry — without changing application code.

What a mesh gives you#

Capability Example
Zero-trust security Automatic mTLS between all workloads; policies like “only checkout may call payments” based on workload identity (SPIFFE IDs)
Traffic management Weighted routing for canaries, header-based routing, mirroring, fault injection
Resilience Timeouts, retries with budgets, circuit breaking, outlier detection
Observability Golden metrics (requests, errors, latency) and traces for every hop

Architectures: sidecar vs sidecarless#

  • Sidecar — an Envoy proxy in every Pod. Full L7 features everywhere, but extra CPU/memory per Pod and restarts to upgrade proxies.
  • Istio ambient mode (GA since Istio 1.24, late 2024) — a per-node ztunnel provides L4 mTLS and identity for all Pods; optional waypoint proxies add L7 features only where needed. Far less overhead and no app restarts to join the mesh.
  • eBPF meshes (Cilium) — use the CNI’s eBPF data plane for L3/L4 and a shared per-node Envoy for L7.

Choosing a mesh#

Istio Linkerd Cilium Service Mesh
Model Sidecar or ambient Lightweight Rust sidecar eBPF + per-node Envoy
Strengths Most features; multi-cluster; Gateway API; ambient reduces cost Simplicity, low overhead, strong defaults One stack for CNI, policy, mesh, observability (Hubble)
Watch out Complexity; learn its APIs Fewer advanced traffic features Ties mesh to the CNI choice

OpenShift Service Mesh is based on Istio.

Do you need a mesh?#

Common mistakes#

Common mistakeRetries at every layer

Client library, mesh and gateway all retrying multiplies load during an outage (retry storms). Retry in one place with budgets and timeouts.

Common mistakeAdopting a mesh for one feature

If you only need ingress routing or metrics, a mesh adds more operational load than value.

Quick check#

What does a service mesh provide? mTLS and workload identity, traffic management, resilience features and telemetry for service-to-service traffic without code changes.

What are ztunnel and waypoint proxies in Istio ambient mode? ztunnel is a per-node proxy providing L4 mTLS and identity; waypoints are optional proxies that add L7 features for selected namespaces or services.

Why consider ambient over sidecars? Lower resource overhead, no per-Pod proxies, no application restarts to join or upgrade, and L7 cost only where needed.

When might you not need a mesh? Few services, no zero-trust mTLS requirement, and needs met by Gateway API, NetworkPolicies, libraries and OpenTelemetry.

Summary#

  • A mesh adds mTLS, traffic control, resilience and telemetry transparently.
  • Sidecarless (Istio ambient, Cilium) is now mainstream and cheaper to run.
  • Choose by need: Istio for features, Linkerd for simplicity, Cilium for a unified eBPF stack — or no mesh.
