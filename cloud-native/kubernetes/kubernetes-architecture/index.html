Kubernetes Architecture: Control Plane, Nodes and Reconciliation

How a Kubernetes cluster works inside — API server, etcd, scheduler, controllers, cloud controller, kubelet, container runtime and kube-proxy — the declarative model and reconciliation loops, what happens on kubectl apply, high availability, managed Kubernetes and versioning.

Simple definition#

Kubernetes is an open-source platform that runs containerised applications across a cluster of machines. You tell it what you want — “run three copies of this image, reachable on port 8080” — and it continuously works to make the cluster match, restarting, rescheduling and replacing containers as machines and workloads change.

The problem it solves#

Running containers on one server is easy. Running hundreds of services across hundreds of servers raises hard questions: Which machine has room? What happens when a machine dies? How do services find each other? How do you roll out a new version without downtime? Kubernetes answers these with a common API and automation, so teams do not script them by hand.

The core idea: declarative state and reconciliation#

  • Every object has a spec (what you want) and a status (what is).
  • Controllers watch objects through the API server and act to close the gap — forever, not once.
  • This is why Kubernetes self-heals: delete a Pod managed by a Deployment and a new one appears, because desired state still says “three replicas”.

Cluster architecture#

Control plane#

Component Role
kube-apiserver The single front door. Every read and write goes through it. Performs authentication, authorisation and admission control, then stores objects in etcd. Stateless and horizontally scalable.
etcd Consistent, distributed key-value store holding all cluster state. Uses the Raft consensus algorithm, so it needs an odd number of members (3 or 5) for quorum. Back it up.
kube-scheduler Watches for Pods without a node, filters nodes that fit (resources, taints, affinity), scores them, and binds the Pod to the best node.
kube-controller-manager Runs built-in controllers: Deployment, ReplicaSet, Node, Job, EndpointSlice, ServiceAccount and more.
cloud-controller-manager Integrates with the cloud provider: load balancers for Services, node lifecycle, routes.

Worker nodes#

Component Role
kubelet Agent on every node. Watches Pods assigned to its node, asks the runtime to start containers, runs probes, reports status.
Container runtime Pulls images and runs containers through the Container Runtime Interface (CRI) — typically containerd or CRI-O. (Docker Engine support via dockershim was removed in 1.24; images built with Docker still run.)
kube-proxy Programs Service routing on the node (iptables or nftables). Many clusters replace it with an eBPF data plane such as Cilium.
CNI plugin Gives each Pod an IP and connects Pod networks across nodes. See networking.

What happens on kubectl apply#

Notice that no component calls another directly — they all watch and update objects through the API server. This loose coupling is what makes Kubernetes extensible.

Extending Kubernetes#

  • Custom Resource Definitions (CRDs) add new object types (for example Certificate, Application, PostgresCluster).
  • Operators are custom controllers that reconcile CRDs — encoding operational knowledge (install, upgrade, back up a database) as code.
  • Admission webhooks and policies validate or mutate objects (security).
  • Aggregated APIs and the Gateway API, CSI, CNI, CRI standard interfaces let vendors plug in without forking Kubernetes.

High availability#

  • Three or five control-plane nodes across zones; etcd quorum survives the loss of one (of three) or two (of five) members.
  • Scheduler and controller-manager run active/standby using leader election.
  • Worker nodes spread across zones; workloads use topology spread constraints and PodDisruptionBudgets.
  • Managed Kubernetes (Amazon EKS, Azure AKS, Google GKE, Red Hat OpenShift on cloud) runs the control plane for you — the default choice unless you have a strong reason to self-manage.

Versions and upgrades#

  • Kubernetes releases about three minor versions a year (1.34 in August 2025, 1.35 in December 2025, 1.36 in April 2026); each is supported for roughly 14 months upstream.
  • Upgrade one minor version at a time: control plane first, then nodes; read deprecation notes; test add-ons (CNI, ingress/gateway, CSI).
  • Recent milestones architects should know: sidecar containers stable (1.33), in-place Pod resize stable (1.35), cgroup v1 support removed by default (1.35), Dynamic Resource Allocation for GPUs and accelerators maturing (stable core in 1.34, more in 1.36), user namespaces GA (1.36), and the retirement of the community ingress-nginx controller in March 2026 in favour of the Gateway API and maintained controllers.

Common mistakes#

Common mistakeTreating Kubernetes as a VM scheduler

Logging into nodes and changing things by hand. Changes vanish when nodes are replaced. Change desired state through the API, ideally through Git.

Common mistakeRunning etcd without backups or with an even member count

Two members cannot tolerate any failure, four tolerate the same as three. Use 3 or 5 and test restores.

Common mistakeFalling several versions behind

Skipped upgrades accumulate risk and unsupported APIs. Budget for a regular upgrade cadence.

Quick check#

What is the role of the API server? It is the only component that talks to etcd and the front door for all reads and writes; it authenticates, authorises and admits every request.

Why does Kubernetes self-heal? Controllers continuously compare desired state with actual state and act to close the gap, so a deleted or failed Pod is recreated to match the desired replica count.

What does the scheduler do? Assigns unscheduled Pods to nodes by filtering nodes that fit (resources, taints, affinity) and scoring the rest.

Why does etcd need 3 or 5 members? Raft needs a majority (quorum) to commit writes; odd numbers maximise failure tolerance — 3 members tolerate 1 failure, 5 tolerate 2.

What is an operator? A custom controller with CRDs that automates the operation of an application, such as installing, upgrading and backing up a database.

What replaced dockershim? CRI-compatible runtimes such as containerd and CRI-O; Docker-built images still run because they are OCI images.

Summary#

  • Kubernetes is a declarative system of control loops around a central API.
  • Control plane: API server, etcd, scheduler, controller managers. Nodes: kubelet, runtime, kube-proxy/eBPF, CNI.
  • Components cooperate only through watching and updating API objects.
  • Extend with CRDs and operators; run HA across zones; prefer managed control planes; upgrade regularly.
