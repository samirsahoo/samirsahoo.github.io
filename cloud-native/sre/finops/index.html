FinOps for Cloud and Kubernetes

Managing cloud and Kubernetes cost as an engineering discipline: the FinOps Framework (principles, phases, domains, scopes), the FOCUS billing standard, Kubernetes cost allocation with OpenCost, rightsizing, autoscaling and bin-packing, spot and commitments, unit economics, FinOps for AI, GreenOps, and platform guardrails.

Simple definition#

FinOps is an operational framework and cultural practice that maximises the business value of cloud (and now technology) spending through collaboration between engineering, finance and business — making cost visible, owned and optimised continuously.

The FinOps Framework#

Principles (FinOps Foundation): teams collaborate; business value drives decisions; everyone takes ownership of their usage; data is accessible, timely and accurate; FinOps is enabled centrally; take advantage of the variable cost model of the cloud.

Scopes extend FinOps beyond public cloud — SaaS, data centres, licensing and AI — and the 2026 framework adds explicit guidance on aligning with executive strategy. FinOps for AI (model API tokens, GPUs, AI platforms) is now a major focus area.

FOCUS: one billing format#

The FinOps Open Cost and Usage Specification (FOCUS) standardises billing data columns (cost, usage, service, region, tags, commitments) across cloud and SaaS providers, so cost tools and dashboards work across vendors. Major clouds publish FOCUS-format exports; check the current spec version before building on it.

Kubernetes cost: the allocation problem#

Cloud bills show nodes; teams own Pods. Kubernetes cost tools split node cost by what workloads request (and use).

  • OpenCost (CNCF incubating) is the open standard and engine; Kubecost and cloud tools build on similar models.
  • Require labels/annotations for team, app, environment and cost centre (enforced by admission policy).
  • Report idle cost (requested but unused, and unallocated node capacity) explicitly.
  • Show cost in the developer portal next to each service.

Optimisation levers#

Lever What to do Typical saving
Rightsize requests Use VPA recommendations / usage percentiles; in-place resize Large — requests are often 2–5× actual use
Autoscale Pods HPA/KEDA; scale to zero for idle non-prod Medium
Bin-pack nodes Karpenter consolidation, fewer larger nodes, right instance families Medium–large
Spot / preemptible For stateless, fault-tolerant and batch workloads Up to ~60–90% on those nodes
Commitments Savings plans, reserved instances, committed use for the steady baseline 20–60% on committed portion
Schedule non-prod Shut down dev/test outside working hours ~65% of non-prod compute
Architecture ARM (Graviton/Ampere/Cobalt), managed services, data transfer design, storage tiers Varies
Observability cost Cardinality, sampling, retention Often significant

Unit economics#

Total cost alone says little. Track cost per business unit: cost per order, per active customer, per API call, per tenant. Unit cost falling while total cost rises is often healthy growth.

FinOps for AI#

  • Track cost per inference / per token / per task, GPU utilisation and idle GPU time.
  • Use AI gateways for per-team quotas and showback; route to cheaper models; cache prompts.
  • Schedule GPUs efficiently (DRA, sharing/partitioning, queueing with Kueue); use spot for training where possible.

GreenOps#

Carbon and cost usually move together: rightsizing, scaling to zero, efficient instance types and choosing lower-carbon regions reduce both. Cloud carbon dashboards and tools like Kepler (Kubernetes energy metrics) make it visible.

Platform guardrails for cost#

  • Required cost labels at admission; default requests via LimitRange; namespace ResourceQuotas.
  • Budgets and anomaly alerts per team; cost shown in Backstage.
  • Non-prod schedules and TTLs for preview environments.
  • Golden-path defaults with sensible sizes and autoscaling.

Common mistakes#

Common mistakeFinOps as a finance-only report

Engineers make most cost decisions. Put cost data in their tools and give them ownership.

Common mistakeInflated requests “just in case”

Requests drive both scheduling and cost. Rightsize with data; rely on autoscaling for peaks.

Common mistakeCommitments before optimisation

Committing to an over-provisioned baseline locks in waste. Rightsize first, then commit.

Quick check#

What are the three FinOps phases? Inform, Optimize and Operate — a continuous loop.

What is FOCUS? The FinOps Open Cost and Usage Specification — a common format for billing data across cloud and SaaS providers.

Why is Kubernetes cost allocation hard and how is it done? Bills show nodes while teams own Pods; tools like OpenCost split node and shared costs by requests and usage using namespaces and labels.

Name three Kubernetes cost-optimisation levers. Rightsizing requests, autoscaling and bin-packing nodes (Karpenter), spot instances, commitments, and scheduling non-prod off.

What is unit economics in FinOps? Measuring cost per unit of business value, such as cost per order or per customer, to judge efficiency as the business grows.

Summary#

  • FinOps makes cost visible, owned and optimised through engineering–finance collaboration.
  • Inform → Optimize → Operate; scopes now include SaaS, data centres and AI.
  • Allocate Kubernetes cost with OpenCost and enforced labels; show cost in developer tools.
  • Rightsize, autoscale, bin-pack, use spot and commitments; track unit economics; consider carbon.
