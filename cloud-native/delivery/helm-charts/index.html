Helm Charts

Helm explained simply: charts, templates, values and releases; chart structure; install, upgrade and rollback; OCI registries; Helm 4 changes (server-side apply, WebAssembly plugins, install by digest); chart best practices, testing, security, umbrella charts, Helmfile, and Helm with GitOps.

Simple definition#

Helm is the package manager for Kubernetes. A chart is a versioned package of templated Kubernetes manifests; values customise it per environment; installing a chart creates a release that Helm can upgrade and roll back.

How Helm works#

Chart structure#

orders/
├── Chart.yaml          # name, version (chart), appVersion (app), dependencies
├── values.yaml         # defaults
├── values.schema.json  # validates values
├── templates/
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── httproute.yaml
│   ├── hpa.yaml
│   ├── _helpers.tpl    # named templates (labels, names)
│   └── NOTES.txt
└── charts/             # sub-chart dependencies

A template fragment:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "orders.fullname" . }}
  labels: {{- include "orders.labels" . | nindent 4 }}
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: orders
          image: "{{ .Values.image.repository }}@{{ .Values.image.digest }}"
          resources: {{- toYaml .Values.resources | nindent 12 }}

Everyday commands#

Task Command
Install / upgrade helm upgrade --install orders oci://ghcr.io/acme/charts/orders --version 1.4.2 -f values-prod.yaml -n shop
Preview helm template … or helm diff upgrade … (plugin)
History / rollback helm history orders -n shop, helm rollback orders 3 -n shop
Lint / test helm lint, helm test orders
Package / publish helm package ., helm push orders-1.4.2.tgz oci://ghcr.io/acme/charts

Helm 4#

Helm 4 (November 2025, Helm’s 10th anniversary) modernised the tool:

  • Server-side apply by default for new releases — better field ownership and conflict detection, aligned with GitOps tools. Releases created by Helm 3 keep client-side apply until changed.
  • WebAssembly plugins — an optional sandboxed plugin runtime; post-renderers become plugins.
  • Install by digest from OCI registries for supply-chain integrity.
  • kstatus-based waiting for resource readiness.
  • Flag changes: --atomic → --rollback-on-failure, --force → --force-replace.
  • Helm 3 charts (apiVersion v2) continue to work.

Best practices#

  • Version charts with SemVer; separate chart version from appVersion.
  • Values schema (values.schema.json) to catch bad values early.
  • Sensible, secure defaults: resources, probes, non-root security context, PodDisruptionBudget.
  • Keep templates simple — heavy logic makes charts unreadable; prefer a few well-named values.
  • Standard labels (app.kubernetes.io/name, instance, version, part-of).
  • No secrets in values files — reference External Secrets.
  • Publish to OCI registries; sign charts (cosign) and verify.
  • Test: helm lint, unit tests (helm-unittest), schema validation (kubeconform), policy checks (Kyverno CLI / Conftest), and install tests in kind/k3d in CI.
  • Library charts for shared templates across many services (a common platform-team pattern).

Composition#

Approach Use
Umbrella chart One chart with dependencies for a whole system
Helmfile Declarative list of releases and values per environment
GitOps (Argo CD / Flux) Git holds chart versions + values; the controller renders and applies — the recommended production approach

Helm with GitOps#

Argo CD renders the chart and applies manifests (it does not create Helm release records); Flux’s Helm controller performs real Helm releases. Either way, Git records which chart version and values run where.

Common mistakes#

Common mistakeRunning helm upgrade by hand in production

Changes are not reviewed or recorded in Git and drift between environments. Let GitOps apply charts.

Common mistakeCharts as programming languages

Deeply nested conditionals and loops make charts impossible to review. Keep charts boring; split them if needed.

Quick check#

What is the difference between a chart, values and a release? A chart is the package of templates; values customise it; a release is an installed instance of a chart with its revision history.

What changed in Helm 4? Server-side apply by default for new releases, WebAssembly-based plugins, install by digest from OCI registries, kstatus waiting and renamed flags such as --rollback-on-failure.

Kustomize or Helm? Helm for distributable, versioned packages and third-party software; Kustomize for overlays of your own manifests — both work with GitOps.

How do you test a chart? Lint, unit-test templates, validate rendered manifests against schemas and policies, and install it in a throwaway cluster in CI.

Summary#

  • Helm packages templated manifests into versioned charts; values customise; releases track revisions.
  • Helm 4 brings server-side apply, Wasm plugins and digest-based installs.
  • Keep charts simple, secure by default, schema-validated, tested and published to OCI.
  • Apply charts in production through GitOps.
