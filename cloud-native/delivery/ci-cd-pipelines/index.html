CI/CD Pipelines and Progressive Delivery

Continuous integration and delivery for cloud native apps: pipeline stages and quality gates, build once and promote, environments, GitHub Actions, GitLab CI, Jenkins and Tekton, DevSecOps scanning, deployment strategies (rolling, blue-green, canary, feature flags) with Argo Rollouts and Flagger, and DORA metrics.

Simple definition#

  • Continuous integration (CI) — every change is merged often, built and tested automatically, producing a versioned artifact.
  • Continuous delivery (CD) — every artifact that passes the pipeline can be released at any time with the push of a button.
  • Continuous deployment — every passing change is released automatically.
  • Progressive delivery — releases are exposed gradually (canary, feature flags) and rolled back automatically if metrics degrade.

The pipeline#

Principles#

  1. Build once, promote the same artifact (by digest) through every environment; only configuration changes.
  2. Fast feedback: commit stage under 10 minutes; slower tests later and in parallel.
  3. Everything as code: pipelines, infrastructure, policies, environments.
  4. Shift security left but also verify at deploy time and runtime.
  5. Small batches: trunk-based development, short-lived branches, feature flags.
  6. CI pushes artifacts; CD pulls desired state — CI should not hold production cluster credentials (GitOps).

Deployment strategies#

Strategy Pros Cons
Rolling (Deployment default) Simple, no extra capacity Mixed versions during rollout; slow rollback
Blue-green Instant switch and rollback Double capacity; database changes must be compatible
Canary Real-traffic validation with small blast radius Needs good metrics and traffic splitting
Feature flags Decouple deploy from release; per-user targeting Flag debt; needs governance (OpenFeature standard)
Shadow / mirroring Test with production traffic, no user impact Side effects must be handled

Argo Rollouts and Flagger automate canary and blue-green on Kubernetes: shift traffic via Gateway API, mesh or ingress, run analysis against Prometheus/Datadog metrics (error rate, latency) and roll back automatically.

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: orders }
spec:
  strategy:
    canary:
      steps:
        - setWeight: 10
        - analysis: { templates: [{ templateName: success-rate }] }
        - setWeight: 50
        - pause: { duration: 10m }
        - setWeight: 100

Database changes#

Expand-and-contract migrations keep old and new versions compatible: add columns/tables first (expand), deploy code that uses both, migrate data, then remove old structures (contract) in a later release. Tools: Flyway, Liquibase.

Measuring delivery: DORA metrics#

Metric Elite performers (indicative)
Deployment frequency On demand, many per day
Lead time for changes Less than a day
Change failure rate Low (single-digit to ~15%)
Failed deployment recovery time Less than an hour

DORA’s research also tracks reliability and shows that speed and stability improve together with good practices.

Common mistakes#

Common mistakeRebuilding the image per environment

You test one artifact and deploy another. Build once and promote by digest.

Common mistakeManual gates for everything

Approvals that rubber-stamp every change slow delivery without adding safety. Automate evidence; reserve human approval for high-risk changes.

Common mistakeCanary without good metrics

If you cannot detect a bad version from metrics, canary analysis passes broken releases. Define SLIs first.

Quick check#

What is the difference between continuous delivery and continuous deployment? Delivery keeps every change releasable with a manual trigger; deployment releases every passing change automatically.

Why build once and promote? So the artifact tested is exactly the artifact released; only configuration differs between environments.

Blue-green vs canary? Blue-green switches all traffic between two full environments for instant rollback; canary gradually shifts a small share of traffic to the new version and analyses metrics before continuing.

What do Argo Rollouts and Flagger do? Automate progressive delivery on Kubernetes: traffic shifting, metric analysis and automatic promotion or rollback.

Name the four DORA metrics. Deployment frequency, lead time for changes, change failure rate and failed deployment recovery time.

Summary#

  • CI builds and verifies; CD makes every change releasable; progressive delivery limits blast radius.
  • Build once, sign, promote by digest; keep cluster credentials out of CI.
  • Embed security scanning at every stage.
  • Use canary/blue-green with automated analysis; measure with DORA metrics.
