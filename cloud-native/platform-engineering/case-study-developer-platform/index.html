System Design: An Internal Developer Platform for 300 Teams

A complete system design for an enterprise internal developer platform: requirements, sizing, architecture, golden-path flow, tenancy model, cluster fleet, delivery, security and compliance, observability, cost, rollout plan, success metrics and trade-offs.

The design brief#

“A bank with 300 delivery teams (about 2,500 developers) runs a mix of VMs and early Kubernetes clusters. New services take six weeks to reach production through tickets. Design an internal developer platform that gets a new service to production in under a day — securely and compliantly.”

1. Requirements#

Functional

  • Self-service creation of services (Java, Node, Python), databases, queues and environments.
  • Standard CI/CD with security scanning, signing and progressive delivery.
  • Catalog of all services with owners, docs, dependencies, runtime status and cost.
  • Environments: dev, test, staging, prod; ephemeral preview environments per PR.

Non-functional

Requirement Target
New service to production < 1 day (target: first deploy to dev in < 15 minutes)
Platform availability 99.9% for CI, registry, GitOps; 99.95% for production clusters
Compliance Segregation of duties, audit trail, change evidence, encryption, EU data residency
Scale ~3,000 services, ~25,000 Pods in production, ~150 deployments/day
Security Signed images only; least privilege; no cluster credentials in CI

2. Sizing (rough)#

  • 3,000 services × average 3 replicas × 0.5 vCPU / 1 GiB → ~4,500 vCPU / 9 TiB requested in prod; plus non-prod ≈ 1.5× → plan for ~12,000 vCPU across environments with autoscaling.
  • Clusters: prod per region (2 regions) split by tenancy class (general, regulated) → 4 prod clusters; non-prod 4–6 clusters; platform/management cluster(s).
  • CI: ~5,000 builds/day peak → autoscaled runners on Kubernetes.

3. Architecture#

Plane Choice Reason
Portal Backstage (or Red Hat Developer Hub) Catalog, templates, docs, plugins
CI GitHub Actions with self-hosted runners (ARC) Close to code; OIDC to cloud; scalable
Registry Harbor or cloud registry, OCI for images + charts + SBOMs Signing, scanning, replication
CD Argo CD (ApplicationSets) + Argo Rollouts Pull-based, multi-cluster, progressive delivery
Release governance Risk-based automated change records; release orchestration for multi-team releases Compliance without blocking
Infra self-service Crossplane compositions (Postgres, Kafka topics, buckets) Capabilities as APIs with defaults
Runtime Managed Kubernetes / OpenShift; Gateway API; Cilium Standard, secure networking
Security Kyverno, Sigstore, External Secrets + Vault, workload identity, Falco Guardrails as code
Observability OpenTelemetry → Prometheus/Mimir, Loki, Tempo, Grafana; SLO tooling Built into templates
Cost OpenCost + cloud billing (FOCUS) in the portal Showback per team

4. Golden path flow#

What the template delivers out of the box: repository with code skeleton, Dockerfile, CI workflow (tests, SAST, SCA, image build, SBOM, signing), Helm/Kustomize manifests with secure defaults, catalog-info.yaml, TechDocs, dashboards and SLO definitions, Argo CD Application, and a database claim if requested.

5. Tenancy model#

  • Namespace-per-team-per-environment on shared clusters; regulated workloads on dedicated clusters.
  • Humans have read-only access to production; changes only through Git (segregation of duties via PR reviews by a second person).

6. Security and compliance#

  • Supply chain: SLSA provenance, cosign signatures, SBOMs, Kyverno verifyImages at admission.
  • Policies: required labels/owners, no privileged Pods, approved registries, resource requests.
  • Secrets in Vault via External Secrets; workload identity for cloud access.
  • Audit: Git history + Argo CD events + API audit logs + automated change records = evidence.

7. Reliability of the platform itself#

  • Platform components have SLOs and on-call; HA across zones; GitOps for platform config.
  • Break-glass access procedure, audited.
  • Disaster recovery: clusters rebuildable from Git; Velero for stateful add-ons; registry replication across regions.

8. Rollout plan#

Phase Scope
0–3 months Thinnest viable platform: one golden path (Java service), CI template, Argo CD, one non-prod and one prod cluster; 3 pilot teams
3–6 months Catalog for all services, database and queue claims, observability defaults, policy enforcement in audit mode
6–12 months 100 teams onboarded; preview environments; enforce policies; cost showback; second region
12+ months Remaining teams; VM migration path (OpenShift Virtualization or rehost); AI-assisted templates

9. Success metrics#

  • Time to first deploy for a new service: 6 weeks → < 1 day.
  • Lead time for changes and deployment frequency (DORA) per team.
  • Golden-path adoption %, platform satisfaction score, tickets per deployment.
  • Policy violations trending down; mean time to recover.

10. Trade-offs#

Decision Choice Alternative
Shared vs dedicated clusters Shared per environment + dedicated for regulated Cluster per team: stronger isolation, much more to operate
Portal Backstage Commercial portal: faster start, licence cost
Infra APIs Crossplane Terraform via pipelines: mature, less real-time reconciliation
CD Argo CD Flux: lighter, fewer UI features
Governance Risk-based automation Manual CAB for all: slower, not safer

TipWhat makes this design strong

It starts thin, measures outcomes, builds guardrails instead of gates, and treats the platform as a product with SLOs — while meeting banking compliance through automated evidence.

Quick check#

Why namespace-per-team-per-environment instead of a cluster per team? It balances isolation with operational cost: quotas, policies, RBAC and NetworkPolicies isolate teams on shared clusters; dedicated clusters are reserved for regulated or special workloads.

How is segregation of duties achieved without manual deployments? All changes flow through Git with mandatory review by another person; humans are read-only in production; GitOps applies changes; audit evidence is collected automatically.

What does the golden-path template include? Repository skeleton, Dockerfile, CI with scanning and signing, manifests with secure defaults, catalog entry, docs, dashboards and SLOs, Argo CD Application and optional infrastructure claims.

Summary#

  • Thin, product-managed platform: Backstage + CI templates + Argo CD + Crossplane + guardrails.
  • Golden paths deliver secure, observable services in minutes.
  • Tenancy by namespace with policies; dedicated clusters for regulated workloads.
  • Compliance through Git, automation and evidence; success measured by lead time and adoption.
