Platform Engineering Fundamentals

What platform engineering is and why it emerged, platform as a product, Team Topologies, cognitive load, golden paths and paved roads, the thinnest viable platform, the CNCF platform maturity model, platform teams and roles, and how AI is changing platforms.

Simple definition#

Platform engineering is the discipline of building and running internal platforms — curated, self-service capabilities for infrastructure, delivery, security and operations — so that application teams can deliver software quickly and safely without each team becoming an expert in Kubernetes, cloud, networking and compliance.

Why it emerged#

“You build it, you run it” DevOps gave teams ownership — and also gave every team the whole cloud native landscape to learn. The result: cognitive overload, duplicated tooling, inconsistent security and slow onboarding.

Platform as a product#

Product practice In a platform team
Know your users Interview developers; map their journeys and pain points
Product manager A platform product owner prioritises by developer value
Roadmap Published; built with users
Adoption is voluntary The paved road must be easier than the alternatives
Measure outcomes Adoption, onboarding time, lead time, satisfaction — not number of tools
Documentation & support Docs, examples, office hours, SLOs for the platform itself

Team Topologies#

  • Stream-aligned teams own a product or value stream end to end.
  • Platform teams reduce their cognitive load by offering internal services.
  • Enabling teams help others adopt practices (SRE, security, testing).
  • Interaction modes: collaboration (temporary), X-as-a-Service (default for platforms), facilitating.

Golden paths and guardrails#

A golden path (or paved road) is an opinionated, supported, end-to-end way to do a common task — “create a new Java service”, “add a Postgres database”, “expose an API” — with security, observability and compliance built in.

  • Optional, not mandatory: teams may leave the path, but then own the extra work.
  • Guardrails, not gates: policies enforced automatically (admission, scans, budgets) instead of manual reviews.
  • Living code: templates are versioned and updated; existing services get upgrades (for example via Renovate or template updates).

The thinnest viable platform#

Start with the smallest thing that removes the biggest pain — sometimes a wiki page with standards and a few templates. Grow the platform from real demand rather than building a large platform up front.

Platform capabilities#

Capability area Examples
Developer portal Catalog, docs, templates, scorecards (Backstage)
Delivery CI templates, registries, GitOps, progressive delivery
Runtime Kubernetes clusters, namespaces, gateways, service mesh
Infrastructure self-service Databases, queues, buckets via Crossplane/kro/Terraform modules
Security Identity, secrets, policies, image signing, scanning
Observability OpenTelemetry, dashboards, alerting, SLO tooling
Cost Allocation, showback, budgets
AI capabilities Model gateways, GPU pools, MCP servers, AI-assisted golden paths

CNCF platform maturity model#

The CNCF Platforms working group’s maturity model assesses five aspects across four levels (provisional → operational → scalable → optimizing):

Aspect Question
Investment How are staff and funds allocated to the platform?
Adoption How and why do users discover and use it?
Interfaces How do users interact with it (tickets → self-service → APIs and portals)?
Operations How are capabilities planned, run and maintained?
Measurement How is feedback gathered and used?

Roles in a platform team#

Platform product manager, platform engineers (Kubernetes, cloud, delivery), SRE, security engineers, developer advocates / technical writers. Size grows with adoption — measured by value delivered, not ticket throughput.

Platform engineering and AI (2026)#

  • AI-assisted golden paths: natural-language requests that produce repositories, manifests and pipelines from approved templates.
  • Platforms for AI workloads: GPU pools, DRA scheduling, model serving, AI gateways — industry surveys in 2026 show many organisations integrating AI workloads into existing developer platforms rather than building separate ones.
  • Agents as platform users: coding agents consume the same APIs, templates and guardrails (for example via MCP servers), so the platform’s guardrails protect against agent mistakes too.

Common mistakes#

Common mistakeBuilding a platform nobody asked for

A big-bang platform designed without users gets bypassed. Start thin, co-design with pilot teams and measure adoption.

Common mistakeRenaming the ops team “platform” without changing the model

If the interface is still tickets, it is not a platform. Aim for self-service APIs and portals.

Common mistakeMandating the platform

Forced adoption hides product problems. Make the paved road the easiest road.

Quick check#

What is platform engineering? Building and running internal self-service platforms that reduce developers’ cognitive load and embed security, reliability and compliance.

What does “platform as a product” mean? Treating developers as customers: understanding their needs, prioritising by value, keeping adoption voluntary and measuring outcomes.

What is a golden path? An opinionated, supported, end-to-end way to perform a common task, with best practices and guardrails built in.

What are the four Team Topologies team types? Stream-aligned, platform, enabling and complicated-subsystem.

Name the five aspects of the CNCF platform maturity model. Investment, adoption, interfaces, operations and measurement.

Summary#

  • Platforms reduce cognitive load by offering self-service capabilities with guardrails.
  • Run the platform as a product; start thin; make the golden path the easiest path.
  • Use Team Topologies; measure maturity across investment, adoption, interfaces, operations and measurement.
  • AI is both a platform capability and a new kind of platform user.
